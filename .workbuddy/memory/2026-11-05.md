## 第二轮：变体规则澄清（同日 14:49）

### 重大定位修正
用户澄清了玩法，发现**他们玩的不是官方规则**，而是一套独立变体。
定位从「卡坦岛线上版」改为「**支持信任玩法的卡坦变体**」。

### 用户给出的 7 条变体（已写入 06-variant-rules.md）
- V-1 掷骰时机自由（可在回合内任意时刻掷）
- V-2 掷骰前可交易 ← 存牌的前提
- V-3 任意玩家可向当前玩家发起交易（非当前玩家之间仍禁止）
- V-4 港口可借用（当前玩家的港口）
- V-5 银行无限资源
- V-6 开局选地限 3 分钟（理由：审视地图时纷争就已开始）
- V-7 口头支票允许，系统不记录不保障，允许毁约

### 核心理念（已写入 06 第 9 节）
这套规则把**信任变成游戏资源**：
- 存牌 = 把牌托付给别人，对方可以赖账
- 借港 = 港口变成可出租资产
- 只能与当前玩家交易 → 当前玩家成为"临时交易所"，可收过路费
- 中间人经济、声誉博弈

### 我的关键判断
- **Q-01 掷骰前必须禁建造**：否则"先建造花掉牌"比存牌更省事，存牌机制会废
- **Q-07 必须允许零对价**：存牌在系统层面就是 A 给 B 牌、B 给 0，与用户"交易就是交换"的表述冲突
- **交易 UI 应极简**：既然语音谈判，网站只做执行。原挂牌+多方竞价方案（v0.1）已砍掉三层
- 新模型：**当前玩家 = 交易所**，所有人向他请求，他审批

## 第三轮：Q-01 / Q-07 裁决（同日 14:58）

### 裁决结果（我两次建议都被推翻，且两次都对）
- **Q-01 = 允许**：掷骰前可建造/交易/打发展卡，回合内动作顺序完全自由。掷骰必须发生但不限位置。
- **Q-07 = 允许**：零对价转移。

### 我漏掉的两个机制（用户的原话点醒的）
**用户原话**：「前期很少结盟，但是后期若有发展到遏制不住的人，剩下的人往往会结盟阻止其速胜。此时就出现了赠予牌/拒绝交易/恶意投7。这样才有意思。」

1. **恶意投 7** = 利用掷骰时机自由，在对手手牌 ≥8 时故意掷骰赌 7。
   - 用户没明说，是我从"恶意投7"这个词反推出来的
   - 这解释了为什么 Q-01 必须允许建造：若禁止，玩家必须先处理手牌才敢掷骰，突然性消失

2. **末期反霸权结盟** = 赠予牌 + 拒绝交易 + 恶意投7 三件套
   - 三种手段都不需要系统支持
   - 精妙制衡：领先者若是当前玩家，联盟内部无法互相输血（因为只能与当前玩家交易）
   - **结论：系统绝不做落后补偿/限制结盟/反垄断检测**

### 架构影响（反而变简单）
状态机从「两段式 PRE_ROLL/POST_ROLL」改为「**单一行动阶段 + hasRolled 布尔量**」。
不需要 PHASE_CHANGED 事件。事件清单已更新。

### 新洞察（写进 06 第 3.2 节）
自己回合可分散存给 3 人；别人回合只能存给当前玩家 1 人 → **手牌 ≥8 在别人回合是脆弱状态**。

## 第四轮：地图原型（同日 15:04）

用户要求先看地图，确认「我的地图印象」与他平时玩的是否一致，再做后面的决策。

用 Chrome headless 截图验证了 4 轮。

### 技术实现（后续可复用，M1 的 board 模块直接用）
- axial 坐标 (q,r)，半径 2 → 19 格，pointy-top 六边形
- `x = SIZE*√3*(q + r/2)`，`y = SIZE*1.5*r` → 自动得到 3-4-5-4-3 排布
- 顶点 = 地块 6 角的像素坐标取整后做 key 去重 → **54 个**
- 边 = 顶点对排序拼接 key → **72 个**（欧拉公式 V-E+F=2 验证通过）
- 边界边（只属 1 个地块）= **30 条**（我一开始错算成 18，导致港口全挤半圈）
- 港口 = 边界边按极角排序后 `round(k*n/9)` 均匀取 9 个

### 视觉要点
- 地块贴合（k=0.999）+ 2.4px 深色描边 → 形成板缝，像实体卡坦
- 沙滩层（k=1.14）只在外圈露出来 → 海岸线
- 数字 6/8 标红，下方画概率圆点（5/36）
- 强盗用深色小人剪影放在沙漠

## 第七轮：确认方向 A + 云服务账号问题（同日 18:01）

### 已确认
**视觉方向 A（木桌手绘）** 采纳。

### 用户提出的关键疑问
「在账号 A 开云服务后，切换账号 / 转移会话，还能用云服务吗？」

### 查证结果（官方文档）
来源：`workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/App-Publishing/Cloud-Services`

明确事实：
- 云服务额度由**会员版本**决定（体验10个应用/5000点 … 旗舰99个/150000点）
- 资源点**按应用独立**计算、独立消耗，按月刷新
- **删除应用 = 数据永久删除**，且「用源码重新创建应用并开启云服务，也无法恢复原应用的数据」
- 下线应用 ≠ 删除，下线不删数据
- 会员降级：已有应用不会因名额超出而停用，但**不能再开新应用**；资源点额度按新版本调整
- 数据可导出：数据库 CSV / 文件下载；**暂停期间不能导出**
- 暂停后数据保留：体验/标准/高级 30 天，旗舰 60 天

文档**未写**"切换账号"场景。我的推断（已在回复中标注为推断）：
- 应用归属于登录账号，换账号 = 看不到原应用
- 本地代码/会话文件不丢，但 applicationId 和云端数据绑在原账号

### 建议
- **不在会切换的账号上开云服务**，等确定长期账号
- 若现在就要开，先建好导出流程

### ⚠️ 顺带发现的技术问题（重要，待确认）
WorkBuddy 云服务提供的是**数据库 / 认证 / 文件存储 / 云函数**，
**没有常驻 WebSocket 服务**。而卡坦的核心是实时同步（房间状态广播）。
`04-architecture.md` 第 8 节写的"v0.2 接云服务"需要重新评估：
- 方案一：数据库实时监听（CloudBase watch）/ 轮询 — 延迟与成本需实测
- 方案二：自建一台小机器跑 WebSocket 服务，云服务只做持久化与认证
- 这个问题必须在 M1 之前定，否则会推翻旁路设计

## 第十五轮：服务端骨架 T1（同日 23:45）

夜间自动化第一轮。基线绿（engine 117 测试），本轮只做 T1。

### 产出 `apps/server/`（23 个测试全绿，tsc 零错误）
- `src/protocol.ts` 消息契约：`JOIN / START / COMMAND / PING`；服务端 `WELCOME / LOBBY / STATE / REJECT / JOIN_FAILED / PONG`
- `src/room.ts` `Room` + `RoomRegistry`：内存持有 GameState，`sync()` 按座位裁剪后广播
- `src/server.ts` 单端口 http + ws，`/health` 返回房间列表；心跳 30s 踢死半开连接
- `src/index.ts` 入口：`PORT` / `HOST` 环境变量，SIGTERM 优雅退出
- `build.mjs` esbuild JS API → `dist/server.cjs` 176KB 单文件（发布只需 node 一条命令）

### 三个关键决定
1. **座位以连接为准**：COMMAND 里的 `seat` 一律被覆盖。否则改 JSON 就能替别人行动。
2. **房间容量默认 4，满员自动开局；未满员时房主发 START**（≥2 人即可）。否则两人局永远开不了。
3. **同名重连回原座位**，原座在线则 `SEAT_TAKEN`。这是 T7「30 分钟保座」的地基，顺手做了。

### 验收（真实 socket 双客户端）
两人加入 → START → 4 次摆位 → 0 号位掷骰 `[2,3]`：两端收到同一 `seq` 的 STATE，骰子、`hasRolled` 一致，
且各自 `view.viewer` 不同、`players[]` 里没有别人的 `resources` 字段。打包后的 `dist/server.cjs` 也用 node 手写客户端复验过一遍。

### 踩坑
- pnpm 11.5 不再读 `package.json` 的 `pnpm.onlyBuiltDependencies`，且 `allowBuilds` 的值必须是布尔；
  写成 `set this to true or false` 占位会一直报 `ERR_PNPM_IGNORED_BUILDS`，并且**连带 `pnpm -r` 的任何脚本都失败**（它会先跑 install 校验）。
- esbuild 的 `.bin` 垫片在本机会把原生二进制交给 node 执行（`SyntaxError: Invalid or unexpected token`），改用 JS API 打包绕过。
- `new URL('./x.ts', import.meta.url).pathname` 会把中文目录名百分号编码，必须用 `fileURLToPath`。这个项目的路径带中文，后面写脚本都会撞上。
