## 3. 人数/地图假设清单（L-0 需冻结）

### 3.1 标准盘（已无歧义）

`rows = [3,4,5,4,3]`，19 格。地形配比木4 砖3 羊4 麦4 矿3 沙漠1；数字 2/12 各1、3/4/5/6/8/9/10/11 各2（共 18，沙漠无数字）；9 港 = 通用4 + 各专用1。现有 `MAP_4P` 与 `PORT_PATTERN` 完全吻合，作为随机生成的**配比来源**复用即可。

### 3.2 扩展盘（30 格 / 2 沙漠）—— 待冻结的数字与港口参数

几何行结构已明确为 **`[3,4,5,6,5,4,3]`**（官方 5–6 扩展在 19 格外圈补一圈得到 30 格）。现有 `buildGeometry(rows)` 已支持任意行结构，`computePorts()` 也按几何自适应，引擎无需改几何核心。

地形配比（指南 §5.2 已确认）：木6 砖5 羊6 麦6 矿5 沙漠2，共 **28 个生产地块**。

**数字袋**：官方 5–6 人扩展自带 28 个数字 token，且规则明确「只使用扩展里的数字 token，不使用基础版的」。配比是 **2/12 各 2 个，3/4/5/6/8/9/10/11 各 3 个**（合计 2+2+8×3 = 28），恰好对应 28 个生产地块。红点（6、8）共 6 个。
来源：[CATAN 官方 5–6 人扩展规则（2021 PDF）](https://catan.com/sites/default/files/2021-08/catan_5-6_basegame_rules.pdf)、[2022 修订版](https://catan.com/sites/default/files/2024-03/Catan%20Game%205-6%20Rules%202022%20240313.pdf)、[token 配比第三方核对](https://gamemason.com/product/circular-number-tokens-5-6-players-amber-bamboo)。

**港口（存在版本冲突，必须冻结）**：
- 本项目现有标准盘是 **9 港 = 4 通用 + 5 专用（每种资源各 1）**。
- 官方 5–6 扩展是在基础版 9 港之外再加 2 个港口标记（1 个通用 3:1、1 个羊毛 2:1），共 **11 港**；英文规则书/社区整理为「5 通用 + 6 专用（其中羊毛 2 个）」。
- 但另一份资料（Seafarers 5–6 规则）写「11 港 = 6 通用 + 5 专用」，与上面相反。来源：[CATAN Seafarers 5-6 规则](https://catan.com/sites/default/files/2021-08/catan_seafarers_5-6_2020_rules.pdf)、[5-6 规则 FAQ](https://settlersboard.com/catan-5-6-rules-faq)。

> ⚠️ 指南 §5.2 要求「港口数量及类型分配应单列配置并核对选定版本，不把标准盘数字袋简单翻倍」。此处**不能自行拍板**，需你选定一种（见 §6 待确认 A）。

**双沙漠强盗初始位置**：指南 §5.2/§5.3 的「服务端在两个沙漠中选定一个，作为地图快照的一部分广播」仍是**待冻结建议**。当前 `createGame()` 会取第一个沙漠，不广播选择依据。

**发展卡**：指南明确「暂保留 25 张是建议，不代表用户另行批准了牌堆改动」。官方 5–6 扩展另加 9 张（6 骑士 + 垄断/丰饶/筑路各 1），本项目**本轮不改牌堆**，仍 25 张（骑士14 胜利点5 垄断2 丰饶2 筑路2）。

### 3.3 跨人数选图的摆位可完成性（L-0 实证，指南 §5.4）

指南担心「8 人标准盘需放 16 座初始村庄，空间非常紧」，并要求决定：是否引入「放置后仍能完成剩余摆位」这一**额外开局约束**，或改为死局恢复流程。

我用现有几何代码做了可复跑实证（[`probe/l0-board-feasibility.mts`](../probe/l0-board-feasibility.mts)）：

| 核对项 | 结果 |
|---|---|
| 标准盘 54 顶点，距离规则下**精确最大独立集** | **27**（≥ 8 人所需 16） |
| 扩展盘 80 顶点，精确最大独立集 | **40**（≥ 8 人所需 16） |
| 随机贪心摆位 2000 局 × 10 种组合（4/5/6/7/8 人 × 2 盘，共 20000 局） | **死局 0**；「落子后剩余容量 < 剩余步数」的前瞻告警 **0** |
| 含道路约束的摆位模拟（4/6/8 人 × 2 盘，共 12000 局） | **死局 0**；「顶点还在但道路用尽」 **0** |
| 「任意 6/8 不共边」构造，标准盘 4 红点 / 扩展盘 6 红点，各 5000 种子 | **失败 0**（且特意把沙漠也算进地块池，属保守估计） |

结论：在现有距离规则与「村庄＋一条相邻道路」规则下，**4–8 人 × 标准/扩展盘的所有组合，静态容量与随机贪心过程都远未触及摆位死局**。指南 §5.4 担忧的「8 人标准盘空间紧」在容量上不成立（27 个可放点 vs 16 座村庄），但它仍会让**优质点位**变少、体验拥挤——这属于「地图质量/体验」问题，不是「无法完成摆位」。

因此 L-0 需要一个明确决定（见 §6 待确认 B）：
- 选项 1：**不引入额外前瞻约束**，按现有距离规则即可；开始前按上述容量结论校验，8 人标准盘允许开（但 UI 提示拥挤、建议扩展盘）。
- 选项 2：仍引入指南建议的「放置后仍能完成剩余摆位」前瞻校验（实现成本更高，且实证显示几乎不会触发）。

> 无论选哪个，指南 §7 的兜底不能省：**系统代放时若无合法候选，必须暂停开局并广播明确错误**，不空转、不跳过、不伪造建筑。

## 4. 顺序与身份：协议变更设计

指南 §6 的关键约束：**排序不能改变玩家身份、私有手牌视图、昵称或重连凭证**。当前设计恰好分离得比较干净，可以沿用：

- `seat`（0..N-1）是稳定身份：`members[].seat`、`sockets: Map<seat, socket>`、`WELCOME.seat`、同名重连 `join()` 都按 seat/name 走，**不随排序变化**。
- `game.players[]` 按 seat 索引；`viewFor(board, game, seat)` 按 seat 裁剪；`PlayerView.players[]` 与 `me` 都按 seat 对齐。
- 因此建议新增独立的 **`actionOrder: number[]`**（seat 的排列），仅用于：
  1. 选地顺序 = `actionOrder + [...actionOrder].reverse()`；`GameState.setup.seat` 存的是 **seat**，不是名次。
  2. 正常回合：`setup` 结束后 `current = actionOrder[0]`；`endTurn()` 沿 `actionOrder` 循环，而非 `current+1 mod N`。
- **不排序 `players[]` 数组**，也不重排 `sockets` 映射。这样私有视图、重连、颜色分配全部天然不串座。
- 颜色扩展到 8 种（`PLAYER_COLORS`），同时补齐 `PLAYER_MARK`（甲乙丙丁戊己庚辛）、`ROAD_DASH`（8 种可区分纹理）、`PLAYER_HEX`。指南 §6 要求「不能仅靠颜色区分」，第二通道必须同步扩展。
- `setupSeatOrder(playerCount)` 目前返回 `0..n-1` 名次序列；建议**保留为「名次→seat」恒等映射的辅助函数**，另新增 `setupSequenceForOrder(actionOrder)` 由服务端传入真实 seat 序列，避免把名次和 seat 混淆（指南 §2 特别指出「数字表示行动名次，不是登录身份或永久座位 ID」）。

## 5. 协议变更设计（L-0 提交，L-1 起实施）

指南 §8 L-5 要求「升级协议时明确旧客户端拒绝/兼容策略，前后端同批构建」。建议 **v3 不兼容升级**（沿用 v2 做法：JOIN 带 `v`，服务端校验严格相等，旧客户端收到 `PROTOCOL_MISMATCH`）：

**客户端 → 服务端（新增/扩展）**
| 消息 | 内容 | 权限 |
|---|---|---|
| `JOIN` | 增加可选 `intent: 'create' \| 'join'`（或服务端按「房间是否存在」推断创建者） | — |
| `READY` | `{ t:'READY'; ready: boolean }` | 本人 |
| `SET_ROOM_CONFIG` | `{ targetPlayers: 4..8, board: 'base'\|'ext', boardChoice: 'auto'\|'manual' }`（替代/扩展 `SET_SETTINGS`） | **仅房主** |
| `REROLL_MAP` | `{ t:'REROLL_MAP' }` | **仅房主** |
| `SET_ORDER` | `{ t:'SET_ORDER'; order: number[] }`（完整 seat 排列） | **仅房主** |
| `RANDOMIZE_ORDER` | `{ t:'RANDOMIZE_ORDER' }` | **仅房主** |
| `START` | 增加 `configVersion`（原子锁定，拒绝并发旧版本） | **仅房主** |
| `COMMAND` | 不变；`PLACE_SETTLEMENT` 仍是「村庄+道路」原子提交 | 当前 seat |

**服务端 → 客户端（新增/扩展）**
| 消息 | 内容 |
|---|---|
| `WELCOME` / `LOBBY` | 增加 `hostSeat`、`targetPlayers`、`board`、`boardChoice`、`ready: boolean[]`、`order: number[]`、`configVersion`、`mapSnapshot`、`mapSeed`、`generatorVersion`、`boardVersion`、`actionOrder`、`setupDeadline`（若已开局） |
| `LOBBY_CONFIG` | 任何配置变化后广播全员，含操作者 seat 与 `configVersion`；收到即清除本地准备态 |
| `MAP_PREVIEW` | 全员同一份地图快照（地形/数字/港口/强盗起点/seed/版本），不各端 `Math.random` |
| `SETUP_TIMER` | `{ step, seat, deadline, serverTime }`；客户端只展示，刷新/重连不能重置 |
| `SETUP_AUTO_PLACED` | 广播「某某超时，系统代放」+ 代放结果，走同一规则入口 |

**服务端权威要求**
- `Room` 新增：`hostSeat`、`targetPlayers`、`boardKind`、`boardChoice`、`ready[]`、`actionOrder`、`configVersion`、`mapSnapshot`、可控时钟 `now()`（已有，用于报价 TTL，可直接复用做 180s 计时）。
- 人数/地图/顺序/重抽变化 → `configVersion++` + 清空全员 `ready`；昵称/在线状态更新不得清准备。
- `START` 校验：`playerCount === targetPlayers`（≥4）、全员 online+ready、房主、`configVersion` 一致、地图可完成性通过；否则 `REJECT` 并回推权威配置。
- 房主断线：保留身份但锁开始按钮，60s 后移交给「最早入房且在线者」；主动离房立即移交；原房主回来不夺回。
- 已开始：拒绝加人、改人数、重排、重抽地图；同身份重连继续允许。
- 计时：用 `gameId + setupStep + version` 防止重复计时器/多次代放；迟到提交在 deadline 后拒绝并回推最新状态；代放走 `applyCommand(PLACE_SETTLEMENT)` 同一入口，均匀选村庄、再均匀选其合法道路。
- 地图 seed **只**用于地图生成；骰子/洗牌继续用独立随机源（`Math.random` 或独立 seed），不复用。
