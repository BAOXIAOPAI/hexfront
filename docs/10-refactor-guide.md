## 1. 已确认的产品决定

| 项目 | 本轮决定 | 实施含义 |
|---|---|---|
| 使用场景 | 朋友约好一起玩，允许双手操作、缩放棋盘 | 保留完整棋盘与策略深度，不改成单手碎片化游戏 |
| 手机方向 | 横屏为主要对局方式；竖屏主要用于入房和等待 | 优先解决横屏短高度；竖屏中仍能查看状态并返回横屏 |
| 视觉 | 海洋岛屿 + 精致插画桌游，温暖清晰、有实体棋子与卡牌质感 | 统一地形、资源、建筑和 UI 的画风 |
| 语音 | 游戏不提供语音；玩家自行后台电话或语音房 | 后台切换、恢复连接和提示不能缺失 |
| 银行、港口 | 不采用拖拽 | 点击选资源、预览兑换结果、确认 |
| 掷 7 弃牌 | 系统计算应弃数量，玩家自己选牌；向上取整 | 不随机代弃；所有人完成前暂停交易 |
| 弃牌期间的行动 | 有人尚未弃牌时暂停建造、交易、兑换与发展卡，仅允许需要弃牌者提交弃牌 | 保留服务端弃牌锁 |
| 强盗待移动 | 所有人弃完后恢复建造/交易/兑换；发展卡须等强盗移动完成才可使用，结束回合前必须完成强盗结算 | 已由用户确认；同步修改引擎与前端，见第 8 节 |
| 掷 7 对报价的影响 | 全部未成交报价立即作废 | 不在弃牌后恢复旧报价 |
| 报价模型 | 支持多条报价并存，按先后查看，可任选处理 | 不采用强制先进先出的成交队列 |
| 报价寿命 | 每条 10 秒 | 服务端判过期，客户端只显示倒计时 |
| 发送冷却 | 每位玩家发送后冷却 3 秒 | 服务端执行，不能刷新页面绕过 |
| 单人报价上限 | 每人最多 1 条有效报价 | 重发替换本人旧报价，重新计时；不得替换别人的 |

“排队”在本文指同时存在多个待处理请求，不表示预留资源、不表示自动接受，也不表示必须处理完第一条才能看后面的。

## 2. 当前实现及问题清单

本节为源码审阅结果。尚未进行本轮真机测试，因此不把遮挡、帧率、后台断连频率写成实测结论。

| P2 | 画面主要按面板、数字、日志组织 | 游戏动作的因果关系不够直观 | `index.html`、`ui.ts` |

### 2.1 现有资产应保留

- 规则引擎的纯函数结构、服务端权威裁决、按玩家生成视图的分层。
- 前端几何、候选位置、资源文案、颜色等可复用纯函数与相应测试。
- 现有地形 SVG 可以作为基础素材，统一画风后复用，不必全部重新生成。
- WebSocket 同源连接与断线后获取完整视图的机制。

保留分层不等于冻结代码。报价队列、期限、掷 7 放行规则必须改服务端/协议/引擎；不能仅在前端放开按钮。

## 3. 本轮范围与暂缓项目

### 必须纳入

1. 横屏对局信息架构、竖屏入房/等待、尺寸与安全区适配。
2. 棋盘平移缩放、点选预览、明确确认、取消和操作反馈。
3. 建造、发展卡、玩家交易、银行和借港的完整前端入口。
4. 多报价、10 秒过期、3 秒冷却、按 ID 处理、掷 7 清空。
5. 自选弃牌与强盗待处理状态的协调。
6. 后台恢复、离线反馈、重连后状态同步。
7. 统一视觉、关键动效、触屏帮助、减少动态效果选项。
8. 浏览器与真机验收；后置补充 PWA。

- 原生 App、小程序迁移、框架迁移、3D/WebGL 改写。
- 内置语音、聊天频道、债务记录、自动履约、资源托管。
- 自动打牌、AI 战术推荐、地块收益排名。
- 建造成功后的服务端撤销、多方撮合、自动接受报价。
- 同时扩展 5–6 人与更大地图入口；先把当前主流程做好，再单独验证密度。
- 新增选地倒计时及超时托管。旧文档提到不代表已有完整实现，本轮不得自行加入。

若公开运营需要持久化和身份恢复凭证，应单独完成对应发布前任务，见第 10 节，不与美术工作混为一项。

## 4. 横屏信息架构

### 4.1 主对局布局

```text
┌─────────────────────────────────────────────────────────────┐
│ 房间/连接  玩家条（当前玩家突出，手牌数/分数可读）  设置/帮助   │
├─────────────────────────────────────────────┬───────────────┤
│                                             │ 我的资源      │
│                 棋盘主舞台                  │ 发展卡入口    │
│          平移、缩放、回到全局                │ 建造 / 兑换   │
│                                             │ 交易及数量    │
│  情境提示：选择路口 / 等待谁 / 强盗待处理     │ 掷骰 / 结束   │
├─────────────────────────────────────────────┴───────────────┤
│ 按需出现：选点确认条 / 简短事件提示（不永久占用厚底栏）       │
└─────────────────────────────────────────────────────────────┘
```

此图是区域关系，不是像素设计稿。右侧行动区建议先以约 160–192 CSS px 做原型，顶部约 40–48px；这些是试验起点，必须按可用高度调整。

- 小横屏避免在棋盘底部再常驻一排高大的扇形手牌。资源使用清晰图标+数量，完整卡面按需展开。
- 抽屉采用侧向展开；长列表内部滚动，确认按钮固定在抽屉底部。
- 选择棋盘位置时收起大抽屉，只留下操作名、成本和确认/取消。
- 低高度下行动区可分组滚动，但当前任务和关键确认不能滚出视野。
- 待处理交易显示“交易 2”之类的入口与轻提示，不把多条报价横幅堆在地图上。
- 玩家手牌总数影响策略，应在玩家条直接可见或一步展开；不能为装饰牺牲辨识度。
- 桌面复用相同动作和状态模型，宽屏可展开详情面板，不另造一套业务逻辑。

### 4.2 竖屏

- 入房、输入昵称、选择房间、等待玩家均可正常完成。
- 开局后显示清晰的横屏建议，同时保留连接状态、回合摘要、设置与恢复入口。
- 旋转不发游戏命令、不退出房间、不丢失待确认选择；重新计算可视区域。
- 不把系统方向锁定或全屏 API 当成必要前提。无法锁定时给出手动旋转提示。
- 若用户临时竖屏接电话，回来仍能看见待处理任务；不能无限重复弹出旋转提示。

### 4.3 全局信息层级

1. 必须立即知道：连接情况、当前玩家、是否轮到自己、当前必须完成的任务。
2. 决策时要看：自己的资源、别人的公开手牌数量、分数、港口、发展卡数量。
3. 按需查看：最近动作、规则说明、卡牌说明、设置。

拒绝原因不能仅写日志；在对应操作附近展示。状态提示不能只靠颜色、音效或 hover。

## 5. 棋盘和输入系统

### 5.1 相机与手势

- 保留 SVG，建立独立相机状态：缩放比例、平移坐标、棋盘中心。收到 STATE 不重置相机。
- 支持单指平移、双指缩放；桌面支持拖动和明确的缩放按钮。缩放围绕手势中心进行。
- 提供放大、缩小、回到全局按钮，不能只靠手势。
- 通过 Pointer Events 管理手势；处理 pointercancel、多指加入、抬起、失焦和旋转。
- 仅棋盘手势区域管理 touch-action；表单、抽屉仍保留正常滚动与输入。
- 超过移动阈值的操作视为拖动，抬手不能触发建造；阈值以 CSS px 定义并真机调整。
- 缩放范围根据最小可读目标和地图边界确定，不提前固定一个对所有尺寸都适用的倍数。

### 5.2 热区与选择

- 普通按钮建议以至少 44×44 CSS px 作为本项目触屏设计目标；这不是声称所有平台单位等同。
- 棋盘密集目标不能靠重叠透明圆无限扩热区。先按屏幕坐标判断最近合法候选，歧义时局部放大或显示候选选择。
- 热区计算使用实际屏幕变换；SVG 中 12.5 的半径不能视为手机上的 12.5px。
- 先预览再确认，确认前不扣资源、不把虚影画成已建成建筑。
- 取消只撤销本地选择；服务端已确认操作不提供本轮未实现的回滚。
- 显示合法候选是帮助操作，不是战术推荐。不自动选“最佳位置”。

### 5.3 渲染稳定性

- 拆分静态地形、道路建筑、强盗、热区、选中预览和效果层。
- 以 tile/edge/vertex 的稳定 key 更新对象，保持负责手势的容器与焦点稳定。
- 优先消除全棋盘无差别重建，不为追求“绝对增量”过度搭建渲染框架。
- 动画期间继续处理权威状态；多次广播不能让动画阻塞规则状态更新。
- 收到更新后重新检查当前选点合法性：仍合法则保留，失效则清除并解释；不得悄悄替用户选另一个位置。

## 6. 完整操作流程

| 流程 | 目标交互 | 关键限制 |
|---|---|---|
| 入房 | 昵称/房间 → 等待 → 开局 | 分享链接带房间及必要接入参数，不带分享者昵称或身份凭证 |
| 开局摆位 | 选村庄 → 选相邻道路 → 整组预览 → 确认 | 显示当前玩家、轮次和剩余摆位；取消不改变服务器 |
| 普通建造 | 选类型 → 看成本/缺口 → 点合法位置 → 确认 | 收到成功再更新实际资源；失败保留可用上下文 |
| 掷骰 | 点击 → 本地按压/等待反馈 → 权威点数 → 产出效果 | 不强制回合先掷骰；不能用动画随机数当结算结果 |
| 结束回合 | 点击 → 清晰确认 → 提交 | 未掷骰或强盗未处理不能结束；显示具体原因 |
| 查看发展卡 | 卡片列表 → 看说明和可用状态 | 当回合购入不可用、已用过一张等原因可见 |
| 购买发展卡 | 成本预览 → 确认 → 私有卡面出现 | 不向他人展示买到的种类 |
| 骑士 | 选地块 → 选可偷玩家/无目标确认 → 提交 | 与掷 7 的强盗待处理状态避免相互覆盖 |
| 垄断 | 选资源种类 → 确认 | 不提供他人隐藏资源推算 |
| 丰饶 | 选两份资源 → 确认 | 允许两份为同一资源，遵循引擎 |
| 筑路 | 预览第一条 → 基于假设第一条选择第二条 → 确认 | 第一步仍是本地预览；单路可提交条件按引擎判断 |
| 银行/自有港口 | 选交出资源 → 显示实际比例 → 选得到资源 → 确认 | 同种兑换禁用，优先复用规则计算，不复制一套不一致比例 |
| 借港代换 | 当前玩家选受益人、资源、结果 → 确认 | 按当前玩家港口比例，扣/加受益人资源；不自动收租 |
| 对局结束 | 胜者、分数、结果摘要、回房间入口 | 不继续接受操作；重新开局能力若服务端未支持应明确另立任务 |

银行兑换现有命令一次兑换一份。第一版可按此交互；若设计批量数量，必须增加原子批量规则，不能循环发命令伪装成一次兑换。

借港界面不能为预校验而请求受益人的完整隐藏手牌。资源是否足够由服务端检查，失败原因只透露完成该操作所需的信息。

## 7. 多报价系统：必须共同改前后端

### 7.1 权限和容量

- 当前玩家可向任意其他玩家报价；非当前玩家只能向当前玩家报价。
- 每位玩家最多一条存活报价，房间最多 N 条；因此当前玩家也不能同时向三人各挂一条。
- 接收方可先处理任意报价，列表按创建时间排序；重发是新报价，排到对应的新位置。
- 报价不锁定资源。可以有多笔使用同一份资源的请求，但接受时必须按最新状态重新校验。
- 允许一侧为零的赠予/索取，禁止两侧同时为空。

### 7.2 生命周期

```text
创建 → 活跃 → 接受成功 / 拒绝 / 撤回 / 过期 / 被本人新报价替换 / 回合结束作废 / 掷7作废
```

- 每条成功创建的报价由服务端分配唯一 ID、创建时间和过期时间。
- 过期时间为创建后 10 秒；到期不得成交，即使清理定时器尚未执行。
- 每位玩家成功发出后 3 秒内不能再发。重发也受冷却，重新连接不能清除冷却。
- 建议无效请求不更新业务冷却；另设传输层滥发限制，避免错误请求绕过负载保护。
- 撤回不退还冷却。重发先验证新请求；新请求失败时保留旧报价，成功后再原子替换。
- 接受、拒绝、撤回都携带报价 ID；过期或已替换的 ID 返回明确原因，绝不操作另一条报价。
- 接受成功后只删除对应报价；其他报价在各自期限内保留，由接受时重新校验。
- 资源不足建议保留该报价至到期并提示；双方可撤回或重新报价。不得默默改变交易数量。
- 掷 7、回合结束、游戏结束时清空所有活跃报价；重连只恢复尚未过期的报价。

### 7.3 并发与消息契约

建议为协议新增或替换以下概念，字段名称由实施时统一：

- `OfferView { id, from, to, give, get, createdAt, expiresAt }`。
- 报价列表快照、列表版本、服务端时间和本人下次允许发送时间。
- `OFFER_ACCEPT/REJECT/CANCEL { offerId }`。
- 报价创建/替换、终止原因与命令结果关联标识。
- WELCOME 与恢复快照包含当前列表及时间基准，不只返回一条 `offer`。

“检查报价是否仍有效 → 校验接收人 → 引擎结算 → 删除该报价 → 广播”应在一次串行处理里完成。两个接受请求、接受与掷 7 同时到达时，以服务端处理顺序裁决；不能只依赖客户端按钮禁用。

报价内容可沿用当前房间内公开模型，但只给收件人突出行动入口。拒绝原因不广播为羞辱性提示。

客户端倒计时用服务端时间差估算；页面从后台恢复后重新同步。不要通过修改本机时钟延长服务器有效期。

### 7.4 移动端展示

- 常驻入口展示未处理数量，不弹多个模态框，不挤占整张棋盘。
- 展开列表显示发起人、“我付出/我收到”、剩余时间和固定位置的操作按钮。
- 对接收人必须转换给/要视角，避免把发起人的“我给”直接当收件人的“我给”。
- 不自动切换正在阅读的报价，不让一条过期后的下一条接受按钮突然顶到手指下面。
- 报价过期后当前详情变为“已过期”，先禁用原操作；用户主动返回列表。
- 发送按钮显示冷却秒数；草稿在冷却期间仍可编辑。
- 重发需再次主动点击。禁止自动每 3 秒续期，这会消解用户要求的短暂报价与防刷屏设计。

## 8. 掷 7、弃牌与强盗

### 8.1 已确认的结算顺序

1. 服务端确认掷出 7，同时清空所有活跃报价。
2. 按当时手牌计算每人应弃数量，8 张起弃一半并向上取整。
3. 玩家自己选牌并提交；没有需弃牌的人则直接进入下一步。
4. 所有人完成弃牌后恢复交易。强盗尚未移动时保留明确待办，必须处理后才能结束回合。

### 8.2 已确认的行动矩阵

用户已确认：弃牌期间继续保留现有引擎“只允许 DISCARD”的行为；所有人弃完后恢复建造、交易和兑换，发展卡须等强盗移动完成后才恢复。

| 状态 | 弃牌 | 建造/银行/借港 | 玩家交易 | 发展卡 | 结束回合 |
|---|---|---|---|---|---|
| 普通行动 | 不适用 | 当前玩家可做 | 至少一方为当前玩家 | 按原规则 | 已掷骰才可 |
| 有人尚未弃牌 | 仅需要弃牌者 | 暂停 | 不能创建或接受 | 暂停 | 禁止 |
| 弃完，强盗待移动 | 不适用 | 当前玩家可做 | 恢复，受冷却约束 | 禁用，完成强盗后恢复 | 禁止 |
| 强盗已处理 | 不适用 | 正常 | 正常 | 正常 | 按原规则 |

发展卡在强盗待移动时暂禁是本轮已确认规则，用于避免骑士二次移动及其他结算冲突。前端应显示“先完成强盗移动”，服务端也必须拒绝此时的发展卡操作，不能仅禁用按钮。

### 8.3 界面要求

- 需要自己弃牌时打开专用面板：应弃、已选、各资源剩余；加减按钮足够大。
- 其他玩家看到谁尚未完成，不能看到对方选了什么。
- 弃牌数量不足或过量时不能提交；失败保留仍有效的选择。
- 自己提交成功后显示等待其他玩家，不重复提交。
- 弃牌完成后收起弃牌面板，明确提示“交易已恢复；本回合结束前需移动强盗”。
- 强盗选择作为独立任务入口，可暂时收起去交易/建造，再回来处理。
- 游戏结束优先级高于普通面板；报价同步清空。不得用 UI 锁死已结束对局。

## 9. 视觉与反馈规范

### 9.1 风格约束

- 海面作为低细节背景，岛屿边界、资源地块、建筑和数字形成明确层次。
- 地形使用统一视角与描边；森林、丘陵、牧场、田地、山脉、沙漠均有独立轮廓特征。
- 数字片和概率圆点保持高可读性，6/8 的区别不能只靠颜色。
- 玩家颜色搭配描边或形状标识，特别验证白色和橙色棋子在浅色地块上的辨识度。
- 资源图标同时用于手牌、成本、报价和产出；不要同一资源出现多种不一致图形。
- 纸卡材质、轻厚度和阴影统一；装饰不进入点击热区，不抢数字对比度。
- 正文选清晰中文字体，特色字体仅用于短标题；避免为了手写感牺牲小字号阅读。

### 9.2 素材与组件交付

视觉阶段应同时交付：默认横屏、建造预览、交易列表/详情、弃牌、强盗待办、发展卡六类状态；另给竖屏入房和桌面展开版。

需要的资产：六种地形、五种资源、三种建筑形态、道路、强盗、骰子点面、发展卡类别、玩家标识、最长路/最大军标识。先定义尺寸、视角、描边和命名，再批量制作；记录素材来源与授权。

CSS 使用语义变量管理背景、文本、边界、强调、危险、玩家色、间距和层级。避免继续在文件尾部不断覆盖旧断点。

### 9.3 动效原则

| 事件 | 反馈 | 不允许发生 |
|---|---|---|
| 轮到自己 | 玩家条突出、短提示 | 只靠声音通知 |
| 掷骰产出 | 点数落定、地块高亮、自己资源增量 | 动画推迟真实状态或展示假结算 |
| 建造成交 | 建筑轻落位、成本扣除反馈 | 服务端未确认就当成功 |
| 交易成功 | 双方收付摘要与自己资源变化 | 暗示口头承诺已获系统保障 |
| 拒绝/过期 | 原操作旁明确解释 | 只在隐藏日志里出现 |

普通交互反馈目标为约 100ms 内开始；结果动画建议控制在约 1 秒内，掷骰整段不超过约 2 秒。以上为设计目标，需性能记录验证。减少动态效果时保留静态高亮和文字。音效可后置、默认策略独立评审，不能影响后台语音。

## 10. 连接、后台与恢复

### 10.1 UI 状态

明确区分：连接中、已同步可操作、连接中断、正在恢复、无法恢复。WebSocket OPEN 不等于已拿到可操作的完整房间状态。

- 离线时立即禁用会改变游戏的操作，保留看盘和帮助；显示持久状态条。
- 普通草稿和相机可以在本地保留，但游戏事实仍来自服务端。
- 不将离线期间的建造、交易接受自动排队重发，避免恢复后意外执行过时意图。
- 返回前台后检查连接、请求/等待完整视图与报价快照；重新校验本地选择。
- 断线发生在提交后、确认前时显示“正在核对结果”，不要直接声称失败或自动再发。
- 建议增加 requestId 和有限期去重结果，使重复点击、重试与结果提示可关联。
- 使用状态版本/序列防止旧更新覆盖新更新；补齐恢复快照的版本信息。

### 10.2 手机语音场景

以 iPhone Safari 与 Android Chrome 的真实电话/语音房测试为准；另覆盖实际分享入口中的内置浏览器。不能承诺浏览器在后台始终联网，也不能承诺来电一定会断开。

测试至少包含：语音在后台、切进语音 App 再回来、锁屏、网络切换、浏览器标签被回收后重开。10 秒报价在后台过期是预期行为，回来不能自动续期。

### 10.3 与公网发布有关的既有边界

- 当前同名重连可取回断线座位；姓名不是身份凭证。邀请链接不要携带自己的 `name`，更稳妥的公网方案应引入不可猜测的恢复凭证并在服务端绑定座位。
- 当前房间驻留内存。服务重启后不能恢复整局，PWA 也不会改变这一点。应选择实现服务端快照恢复，或在受控试玩中明确接受此限制。
- 协议已有版本字段，但当前 JOIN 解析未保留 `v`；协议升级时必须检查整个收发链路，不能只递增常量。
- 公共分数现在使用含胜利点卡的 `scoreOf()`。补发展卡展示时应单列信息公开规则核对，不能自行假定“所有隐藏胜利点已隐藏”。这不是本轮擅自改变计分规则的授权。

上述事项应有独立任务和测试，不以“纯前端换皮”为由忽略，也不要求本轮文档工作实现。

## 11. 推荐代码职责

| 层 | 职责 | 改造策略 |
|---|---|---|
| engine | 合法性、资源、弃牌、强盗、胜负 | 尽量复用；只对确认的规则变更修改并补回归 |
| protocol | 命令、报价 ID/快照/时间、错误、版本 | 与服务端同步迁移，不兼容升级必须可识别 |
| server | 报价队列/期限/冷却、身份、广播、重连快照 | 作为交易时序与校验权威 |
| net | 连接状态、重试、前后台恢复、命令结果关联 | 不悄悄吞掉用户命令、不盲目重放 |
| 前端状态协调 | 权威视图 + 本地交互状态 + 动画事件 | 三者分离，不把选择草稿当真实游戏状态 |
| board | 相机、输入、地形、棋子、热区、预览 | 稳定容器和分层更新 |
| panels | 建造/交易/弃牌/发展卡/兑换等 | 按领域拆分 ui.ts，避免生成新的巨型类 |
| layout/theme | 横竖屏结构、tokens、组件样式 | 以新布局替换冲突规则，不追加无穷覆盖 |

建议按职责逐步拆文件，不预先创建大量空目录。保持现有原生 TS，只有明确遇到状态组合或维护瓶颈时再评估框架迁移。

## 12. 分阶段实施与完成门槛

### 阶段 A：建立基线与规则契约

- 确认源码入口与当前构建产物关系，记录现有浏览器画面及关键流程。
- 当前目录未检测到 Git 仓库。实施前建立可恢复版本基线；本轮不执行初始化或提交。
- 跑现有 test/typecheck/build，记录实际结果，不沿用旧文档测试数量。
- 将第 1、7、8 节转成报价和行动权限测试用例；先覆盖旧报价接受竞态。
- 将第 8 节已确认的行动矩阵纳入规则基线，并明确第 10 节独立发布事项的采用范围。

完成门槛：现状缺陷与目标行为分开记录，有可恢复基线，核心规则不再靠相互矛盾的注释判断。

### 阶段 B：横屏交互原型

- 先实现隔离原型或可切换的新布局，使用确定性数据覆盖默认、建造、交易、弃牌、强盗待办。
- 验证 667×375 等低高度下的棋盘面积、确认按钮、交易列表和软键盘。
- 测试点选/拖动区分、缩放和候选消歧；优先做到能操作，再进入完整美术。

完成门槛：真机可以稳定选中目标，不依靠精细点按；状态和错误始终可见，关键面板不遮住所需对象。

### 阶段 C：协议与服务端规则

- 落地多报价、ID、过期、冷却、替换、清空、恢复快照和错误码。
- 放开弃牌完成后的建造/交易，同时保留强盗完成前的结束限制。
- 接入命令确认/拒绝与版本策略，补并发和时钟边界测试。

完成门槛：不依靠 UI 也能验证越权、过期和重复请求不会错误成交。

### 阶段 D：前端完整流程

- 接新协议和相机，逐项完成第 6 节所有入口。
- 修复回合外报价入口，显示可选对象和冷却。
- 接入断线恢复、待处理提示、触屏说明、焦点管理。
- 以一次完整多人对局验证，不能只通过截图宣布完成。

完成门槛：无需开发者控制台即可从入房到结束，所有核心行为有入口、有反馈、有错误恢复。

### 阶段 E：美术与体验打磨

- 将验证通过的布局应用统一素材、组件、动效。
- 复核白色玩家、中文长昵称、较大资源数、多个报价和低高度布局。
- 性能采样发现瓶颈后再优化，不因为“游戏”二字直接切换渲染技术。

完成门槛：全部关键状态风格一致、信息清晰；动效不影响输入与服务器状态同步。

### 阶段 F：PWA、发布与回退

- 配置 manifest、图标和独立窗口体验，安装引导按浏览器能力显示。
- 如引入 Service Worker，只缓存适合的静态资产；不缓存 WebSocket 状态，不把离线壳当可离线对局。
- 更新提示避免在对局中强制刷新；验证旧缓存与新协议不兼容时的恢复路径。
- 新旧协议不能混用。优先独立测试环境验证；发布需安排活动房间排空或兼容方案。
- 回退必须包含匹配的前端和服务端版本。回退代码不等于能恢复内存中的旧对局。

完成门槛：浏览器链接可玩、安装后可玩、更新可恢复；有明确发布范围和回退步骤。

## 13. 验收矩阵

### 13.1 设备与视口

| 场景 | 建议尺寸/设备 | 重点 |
|---|---|---|
| 小横屏 | 667×375 CSS px | 操作栏高度、抽屉滚动、确认位置 |
| 常见横屏 | 844×390、932×430 | 安全区、棋盘精度、报价列表 |
| 竖屏 | 375×667、390×844 | 入房、等待、旋转提示、键盘 |
| 平板 | 1024×768 附近 | 布局过渡、面板宽度 |
| 桌面 | 1366×768、1440×900 | 鼠标、键盘、焦点与宽屏信息展开 |
| 真机 | 至少一台 iPhone、一台中低端 Android | 双指、后台语音、网络切换、可读性 |

模拟视口不是实机替代。自动化需核对实际 viewport 与 CSS 像素，不能只设置浏览器外窗大小。

### 13.2 功能与异常用例

- [ ] 非当前玩家可以报价给当前玩家，不能给其他非当前玩家。
- [ ] A/B/C 同时报价均可存在，不互相覆盖；每人最多一条。
- [ ] 3 秒内重复发送被服务端拒绝；刷新/重连不绕过冷却。
- [ ] 冷却后重发生成新 ID，旧 ID 不可接受，10 秒重新开始。
- [ ] 报价到期边界、客户端慢时钟、定时清理延迟时均不能误成交。
- [ ] 接受与掷 7、回合结束、本人重发交错时只执行正确结果。
- [ ] 两条报价争用资源时不会出现负数或重复扣减。
- [ ] 赠予与索取可提交，空换空不可提交；收件人视角正确。
- [ ] 掷 7 清空全部报价，所有人弃完前不能报价或成交。
- [ ] 9 张弃 5 张，玩家自行选择；他人不知道弃牌构成。
- [ ] 有人尚未弃牌时，建造、交易、兑换和发展卡均被服务端拒绝。
- [ ] 所有人弃牌后可建造/交易/兑换，强盗未处理不能结束回合或使用发展卡；强盗处理完成后恢复发展卡正常规则。
- [ ] 缩放、平移时收到 STATE，不回到初始镜头、不触发误建造。
- [ ] 建造确认前收到他人更新，失效候选被撤销并说明原因。
- [ ] 买发展卡、四种行动卡、银行、借港均有可用入口和失败提示。
- [ ] 长报价过期后接受按钮不会移动到下一条并造成误点。
- [ ] 网络在提交前/后分别中断，不静默丢操作、不重复成交。
- [ ] 电话/语音后台返回后，资源、当前玩家、强盗任务、报价与服务端一致。
- [ ] 横竖屏切换不丢座位，不提交草稿，不无限弹提示。
- [ ] 帮助可点击，焦点可见；不靠 hover/颜色/声音传递唯一信息。
- [ ] 减少动态效果时仍能理解产出、成交、建造与轮次变化。

### 13.3 测试分工

- engine 单测：弃牌锁、强盗待办放行/禁止、发展卡冲突与胜负不回归。
- server/protocol 测试：报价时钟、ID、权限、替换、恢复、冷却与竞态，使用可控时钟避免真实等待。
- 前端单测：候选消歧、坐标转换、权限呈现、草稿失效、给/要视角转换。
- 浏览器集成：多页面模拟多人、端到端接受报价、旋转/断线/恢复；不连接正式玩家房间造数据。
- 真机人工：手感、误触、语音并行、浏览器栏、安全区与键盘，这些不由截图测试替代。
- 性能记录：交互反馈、拖动帧时间、长任务、首屏资产大小；先记录基线再定预算，不能凭代码长度推断性能。

常规实施校验命令为 `pnpm test`、`pnpm typecheck`、`pnpm build`。按改动运行相关模块测试，集成阶段再跑全量；本轮没有运行这些命令。

## 14. 实施时禁止误读的事项

1. 横屏优先不等于只用宽度断点判断手机；大手机横屏可能超过旧的 900px。
2. PWA 不保证后台常驻、不自动修复触屏、不保存服务端内存房间。
3. “本地不存规则状态”不禁止保存相机、草稿、焦点或预览；这些属于 UI 状态。
4. 后端权威不禁止前端显示可用动作；前端提示可以过时，服务端仍须最终校验。
5. 全量广播视图可以继续用；它不要求全量重建 DOM。
6. 多报价不等于多个覆盖全屏的弹窗；容量增长必须被列表与聚合提示吸收。
7. 资源卡美术不能泄露别人手牌；发展卡购买反馈也不能泄露种类。
8. 不以“所有旧测试必须原封不动”为目标。确认的规则变更需要更新相关断言，其余规则仍做回归保护。
9. 不把优化指南当部署授权，不在改造过程中反复覆盖现有线上游戏。
