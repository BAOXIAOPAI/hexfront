# 交易系统与交互设计

> 版本 **v0.2** · 2026-11-05（v0.1 的挂牌/竞价模型已被语音方案推翻，见第 3 节）
> 前置阅读：`01-PDR.md` 第 2 节、`06-variant-rules.md` 第 4 节
>
> 本文档回答一个问题：**凭什么别人要玩你这个，而不是 colonist.io？**
> 答案只能在这里。如果这套设计做不出来，项目就没有存在必要——所以这份文档的评审标准是「你自己作为资深玩家，看了想不想玩」。

> ⚠️ **v0.2 重大修订**：v0.1 假设"谈判在站内完成"，据此设计了挂牌 + 多方竞价 + 还价 + 意向广播四层机制。

> 第 1 节的诊断仍然有效（它解释了"为什么站点不该承担谈判"），第 3、4 节已重写。

## 1. 诊断：线上交易为什么慢

把实体桌的一次交易拆开看，它其实是 4 个动作：

```
① 发起     "谁有多的麦？"          → 1 秒，向所有人广播
② 应答     "我有，你要给什么？"    → 1 秒，多人同时回应
③ 议价     "一块石头行不行 / 加块木" → 2~5 秒，来回 1~2 轮
④ 成交     交换资源                → 1 秒
```

合计 **5~8 秒**，且其中 ② ③ 是**多方并行**的。

现在看线上版（以 colonist.io 为代表）的同一件事：

```
① 发起     点开交易面板 → 选给什么 → 选要什么 → 提交      → 8 秒
② 应答     提案挂在某人面前，等他发现并点开               → 5~30 秒
③ 议价     对方拒绝 → 重新开一个提案 → 再等                 → 10~40 秒
④ 成交     点接受                                        → 2 秒
```

**慢的不是网络，是交互范式。** 线上版把「广播 + 并行 + 模糊」的对话，压缩成了「点对点 + 串行 + 精确」的表单。

三个具体病灶：

| 病灶 | 具体表现 |
|---|---|
| **串行化** | 三个人都想换，但提案只能一个个发给某个人，发起者必须挨个问 |
| **精确性强迫** | 必须一开始就说清"给 1 石要 1 麦"，无法表达"我想要麦，价格好商量" |
| **回合外失活** | 不轮到你时界面完全静止，只能干等——而实体桌上你一直在参与讨论 |

## 2. 设计目标（可验收）

| 目标 | 量化标准 |
|---|---|
| 发起一次交易 | ≤ 3 次点击 |
| 从发起到成交（有人愿意的情况下） | ≤ 10 秒 |
| 一次提案可触达的应价方 | 全部其他玩家，并行 |
| 回合外玩家的可参与度 | 至少 3 种有效动作 |
| 误操作率 | 每局 ≤ 1 次 |

## 3. 核心模型修正（v0.2 · 语音为主）

### 3.0 前提变了，结论正好相反

v0.1 的假设是：**谈判在站内完成**。所以 UI 必须承担"并行、模糊、多方"的对话能力，于是设计出挂牌 + 多方竞价 + 还价 + 意向广播四层机制。

你的方案是：**语音谈，网站执行**。

这个前提一变，结论正好反过来：

| | v0.1 假设 | v0.2 实际 |
|---|---|---|
| 谈判在哪 | 站内 | 语音（外部） |
| 网站职责 | 承担谈判 | 只负责执行与记账 |
| 交易 UI | 应该丰富 | **应该极简** |
| 竞价 | 靠 UI 并列展示 | 靠语音自然发生 |

**所以 v0.1 的四层机制，砍掉三层。**

### 3.1 新模型：当前玩家 = 临时交易所

因为「只能与当前玩家交易」（V-3），所有交易必然围绕当前玩家 P 发生。

```
A、C、D 在语音里都听到 P 有意向
        ↓ 各自向 P 发起请求（网站操作）
   ┌─────────────────────┐
   │   P 的交易面板        │
   │   · A: 1石 ⇄ 1麦     │
   │   · C: 2木 ⇄ 1麦     │
   │   · D: 1砖 ⇄ 1石     │
   └─────────────────────┘
        ↓ P 挑一个成交 / 还价 / 全部拒绝
```

**「多方竞价」没有消失，它变成了「多方申请 + 单方审批」。**

这比原设计更好，三个理由：
1. 完全符合规则（交易必须经过当前玩家）
2. P 天然是"选择者"，符合实体桌的权力结构
3. 实现从"广播 + 分支树"降为"一个列表"

### 3.2 三条路径

| 路径 | 场景 | 流程 |
|---|---|---|
| **定向交易**（主） | 语音里已谈好 | P 选对象 → 填给/要 → 发送 → 对方一键接受 |
| **请求交易** | 非当前玩家主动想换 | 非当前玩家填给/要 → P 收到 → 接受/还价/拒绝 |
| **挂牌**（P1，可选） | 有人没开语音 | 挂在侧栏，谁都能接 |

主路径是**定向交易**——绝大多数交易在语音里谈完了，网站只需要"记下来并执行"。

### 3.3 极简原则

- 定向交易 **3 步内**完成（选人 → 填条件 → 发送）
- 请求列表**一屏看完**，不分页不折叠
- **不做成交动画**，只更新数字
- **不做确认弹窗**（唯一例外：结束回合）

### 3.4 明确砍掉

| 砍掉 | 理由 |
|---|---|
| 多方竞价并列展示 UI | 语音里已经竞价了，UI 再并列会出现"语音说好给 A、UI 上被 C 抢掉"的混乱 |
| 意向广播 | 语音说一句就行，做个 UI 反而多余 |
| 还价链的分支树 | 简化为单层"当前条件"，AB 来回改几次足够，不需要可视化历史 |
| 交易历史面板 | v0.2 再说 |

### 3.5 语音带来的实践问题（提前预警）

**手机 + 语音的组合在移动端体验很差**，这是真实的坑：

- iOS 切到微信语音，浏览器页面被挂起，回来时 WebSocket 已断
- 免提开着，游戏音效和语音互相干扰
- 安卓多数机型会直接杀掉后台标签页

**解法（按优先级）**：
1. **桌面端为主**——电脑开两个窗口（游戏 + 语音网页版），零冲突
2. 手机玩 + 另一台设备开语音
3. 站内语音（你说麻烦，同意，v0.1 不做）

这不影响开发，但**直接影响"朋友愿不愿意开第二局"**。如果大家只能用手机，产品里可能需要明确建议"用电脑玩"。

## 4. 交互流程（精简版）

### 4.1 定向交易（P 发起）

```
底部资源条 → 点"交易"
→ 选对象（4 个头像横排，一眼看清）
→ 填"我给"和"我要"（点图标加减，任意一方可为 0 张）
→ 点"发送"
→ 对方弹出：┌ A 想用 1 石 换你的 1 麦 ┐ [接受] [还价] [拒绝]
→ 接受 → 资源立即转移 → 双方看到提示条
```

**关键细节**：允许「我给 0 张」或「我要 0 张」——存牌必需（见 `06` 的 Q-07）。

### 4.2 请求交易（非 P 发起）

```
非当前玩家点"我要交易"（按钮常亮，不因非回合而禁用）
→ 填给/要
→ 发给当前玩家 P
→ P 的交易面板出现一条待处理
→ P 接受 / 还价 / 拒绝
```

> ⚠️ **这要求"交易"按钮对非当前玩家也常亮。** v0.1 设计中回合外玩家不能交易，现在可以"发起请求"了——这是 V-3 的直接后果，不要沿用旧设计。

### 4.3 成交公示

```
全体收到轻提示："A 用 1 石换了 P 的 1 麦"（1.5 秒淡出）
```

保留公示：实体桌上交易是公开可见的。**不公示"谁被拒绝了"**（D-11）。

### 4.4 银行 / 港口快捷入口

常驻按钮，不打开交易面板：

- **4:1** — 自动选你手上最多的那种资源
- **3:1 / 2:1** — 有对应港口时自动出现
- **借港代换** — 当前玩家替他人执行（规则见 `06` 第 5 节）

### 4.5 存牌的专属交互

因为存牌是本项目的核心玩法，交易面板需要一个专门的小功能：

```
交易面板 → 勾选「代管」（可选）
→ 界面标记为"存牌"，成交后显示在侧栏：
   ┌ 代管中 ─────────────┐
   │ P 代 A 保管：木2 砖3  │
   └────────────────────┘
```

> ⚠️ **注意：这个"代管"标记只是界面提示，不是系统债权。**
> 系统不记录"谁欠谁"，也不做归还校验——归还仍然是普通交易。这符合 `06` 第 6 节「不做口头支票系统」。
> 它存在的唯一理由：让玩家自己看得见"我手上有一堆是别人的"，避免记混。这是我建议加的，可以不实现（Q-08）。

## 5. 信息呈现设计

### 5.1 原则

**只呈现实体桌上能看见的。**（PDR 的 P4）

| 信息 | 实体桌 | 线上方案 |
|---|---|---|
| 自己的手牌 | 看得见 | 底部常驻，5 列，数量大字 |
| 他人手牌数量 | 数得出来 | 显示数字徽标（如 `×7`） |
| 他人手牌构成 | **看不见** | **不显示，也不做任何推算** |
| 已建路/村/城 | 看得见 | 棋盘上直接呈现 + 侧栏统计 |
| 已打出骑士数 | 数得出来 | 侧栏数字 |
| 分数 | 公开 | 顶部常驻 + 可展开构成 |
| 谁有哪些港口 | 看得见 | 棋盘上港口图标 + 侧栏列表 |
| 骰子概率分布 | **圆片上的点数可见** | 地块上显示点数圆点（6/8 五个点） |

> ⚠️ 最后一行是个**保守选择**：很多线上版会额外显示"该地块出产概率百分比"或"这块地期望收益 3.2/轮"。我认为**不显示**——实体桌上需要你自己算，这是游戏的一部分。若你要显示，见 **D-02**。

### 5.2 掷骰的仪式感

实体桌掷骰是有期待感的。线上如果只是"数字跳出来"，会失去这个瞬间。

```
点击"掷骰"
→ 骰子动画 0.7 秒（可点击跳过）
→ 骰子定格 + **所有匹配数字的地块同时高亮**（描边发光 0.5 秒）
→ 轻提示条："木+3 砖+1 麦+4 矿+2"（分玩家列出）
→ 手牌数字滚动增长
```

**"高亮匹配地块"是必要的，不是装饰**：实体桌上你一眼扫过去就知道哪些地有 6，线上如果没有这个高亮，玩家需要自己找，认知负担反而更高。

**总耗时目标 2 秒内**（P2）。

### 5.3 掷出 7 的处理

掷 7 是全桌最紧张的时刻，交互要特殊处理：

```
掷出 7
→ 骰子动画 + 红色调闪烁
→ 「弃牌阶段」：所有手牌 ≥8 的玩家进入弃牌界面（其他人看到"等待 X 位玩家弃牌"）
→ 全部提交后：统一揭示"每人弃了多少"（不揭示弃了哪几张）
→ 「移动强盗」：掷骰者的棋盘进入放置模式，所有合法地块高亮
→ 「抽牌」：高亮所有相邻有建筑的玩家，点击选择
```

**关键**：弃牌阶段其他人**能看见"谁还在选"**，这会制造实体桌上那种"你手牌肯定很多"的推理乐趣。但**看不见弃了什么**。

## 6. 建造与操作交互

### 6.1 建造模式

```
点"建造" → 选类型（路/村/城，不可建的灰显并标注原因）
→ 棋盘进入放置模式，所有合法位置**高亮呼吸**
→ 点击位置 → 预览（显示扣什么资源）→ 确认
```

**不可建时给出具体原因**，这是新手和老手都需要的：
- "资源不足：缺 1 矿石"
- "此处与已有村庄相邻"
- "道路未连通"
- "村庄已达上限 5"

### 6.2 防误触

| 操作 | 策略 |
|---|---|
| 建造 | 需点选位置 + 确认（2 步） |
| 交易接受 | 单步，但按钮位置固定、不随内容浮动 |
| 打出发展卡 | 单步，但需从手牌区拖出或长按（避免误点） |
| 结束回合 | 需二次确认（"确认结束回合？"），因为误点代价最大 |
| 撤销 | 建造可 3 秒内撤销（资源退还），交易不可撤销 |

### 6.3 移动端布局（竖屏优先）

```
┌────────────────────────┐
│ 顶部：分数条（4人）      │  ~60px  固定
├────────────────────────┤
│                        │
│      棋盘（SVG）        │  自适应  主体
│      可缩放/平移        │
│                        │
├────────────────────────┤
│ 交易请求区（可收起）      │  浮层
├────────────────────────┤
│ 手牌：木 砖 羊 麦 矿     │  ~110px 固定
│      3  2  1  4  0      │
├────────────────────────┤
│ 操作：掷骰 / 建造 / 交易  │  ~70px  固定
└────────────────────────┘
```

**棋盘交互**：支持双指缩放、单指拖拽。在手机上，19 格的棋盘需要约 1.3 屏宽才能点准顶点，所以缩放是必需的，不是加分项。

**顶点点击热区**：视觉上顶点很小，但点击热区要放大到至少 44×44px（Apple HIG 标准），且相邻顶点热区不能重叠——这需要视觉位置和热区做偏移映射。

> ⚠️ 这是移动端最容易翻车的地方：**顶点太密，点不准**。54 个顶点在 375px 宽的屏幕上，平均间距不到 40px。可能需要"点选后显示候选列表"的兜底方案。

## 7. 回合外玩家的可做之事

这是被严重低估的体验问题。一局 4 人卡坦，你平均有 **75% 的时间在等**。

| 可做 | 说明 |
|---|---|
| **向当前玩家发起交易请求** | **核心（V-3 新增，v0.1 原本禁止）** |
| 回应当前玩家的定向交易 | 核心 |
| 借当前玩家的港口 | 核心 |
| 查看任意玩家的分数构成 | 信息 |
| 查看棋盘任意地块信息 | 信息 |
| 查看操作日志 | 记录 |
| 缩放 / 浏览棋盘 | 沉浸 |
| ~~建造~~ | 规则禁止 |
| ~~与其他非当前玩家直接交易~~ | 规则禁止（必须经过当前玩家） |

**建议**：回合外时，建造按钮灰显并显示"等待 A 行动"，但**交易按钮保持常亮**——这是 V-3 带来的关键差异，别沿用旧设计。

## 8. 实现成本评估（v0.2 修订后）

原方案被我判为"高成本"，改为语音为主后大幅降低：

| 模块 | 复杂度 | 说明 |
|---|---|---|
| 定向交易（选人 + 填条件 + 发送） | 低 | 纯粹的表单 + 状态变更 |
| 请求列表（当前玩家审批） | 低 | 一个队列，无分支 |
| 还价（单层） | 低 | 覆盖条件即可，无分支树 |
| 借港代换 | 中 | 权限判断 + 双账户操作 |
| **并发正确的资源转移** | **中** | 仍存在，但场景已大幅收敛 |

> ⚠️ **并发竞态仍在，但比原方案轻得多。**
> 原方案要处理"多人同时应价一张挂牌"，现在变成"多人同时向 P 发请求，P 逐个处理"——请求本身不改状态，只有 P 点"接受"才发生转移，天然串行。
> **唯一残留的竞态**：P 同时接受两条请求，而资源只够一条。由服务端串行裁决 + 二次校验解决（同前）。

**结论**：交易系统的实现复杂度从"中高"降到"中低"。这是采用语音的直接收益。

## 9. v0.1 的三个疑问，现状

三个问题里有两个已经被你的方案消解了：

| 原疑问 | 现状 |
|---|---|
| 多方竞价会不会让交易"太容易"？ | **消解**——语音里竞价，UI 只做审批，不存在"零成本比价" |
| 意向广播会不会破坏博弈？ | **消解**——不做这个功能了，语音说 |
| 交易公示的粒度？ | **仍待裁决**（D-11） |

**剩下真正需要你拍板的，是交易系统的形态**，已登记为 **D-01（修订版）**：
是采用本文的「当前玩家 = 交易所」模型，还是保留挂牌机制作为补充？我倾向**只做前者**，因为它更简单也更贴合你们的实际用法。
