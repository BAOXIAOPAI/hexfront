# 晴湾纸雕原型：第二轮优化任务书

> 2026-11-10。基于用户反馈和普通对局、交易、弃牌画面的浏览器评审。
> 本文件是待实施要求，不代表代码已修改或验收通过。本轮只写文档。
> 目标原型：`design/desktop/papercut.html`；状态入口：`design/desktop/papercut-states.html`。
> 延续 `19-desktop-first-guide.md` 的桌面优先范围及规则契约。

## 1. 本轮结论和范围

保留“晴湾纸雕”的海面、岛屿、纸质卡牌与实体棋子方向，不重新选风格。重点改善交易操作、文字可读性、视觉层级，并加入适量游戏动效。

本轮先优化独立原型，不修改 `apps/`、`packages/`、正式协议或规则，不部署。原型模拟与真实游戏的边界继续明确标注。

用户已确认的意图：朋友先通过外部语音谈好，再在游戏中执行交易。因此编辑交易不应像复杂表单；改为先选择想收到的资源，再选择自己给出的资源，使用图形化资源卡和拖动数量条。

用户希望在实现成本适中的前提下丰富动效。采用轻量 CSS/SVG/浏览器动画即可，不引入 3D 引擎或物理模拟。本文件中的具体时长、布局和快捷数量是建议默认值，可按原型实测微调。

## 2. 交易重设计：分步、图形化、可回看

### 2.1 统一用词

- 第一步：**我想收到**。
- 第二步：**我愿给出**。
- 最终按钮：**发送给「玩家名」**。
- 避免单独使用“报价”指代某一侧，防止混淆收与付。

交易对象放在面板顶部，始终可见。权限沿用现有规则：当前玩家可选其他玩家，非当前玩家只能向当前玩家发起。切换对象时保留资源草稿，但重新检查权限与可发送性。

### 2.2 第一步：我想收到

展示 5 种资源，每种使用图标、名称、醒目数量与整数滑条。一次只编辑这一侧，不同时展示收付两套共 10 行控件。

每一行建议结构：资源图标与名称 → 数量 → 滑条；保留紧凑的减/加按钮，支持点按和键盘精确调整。拖动不是唯一输入方式，避免数量相差一张时反复拖动。

五种资源均可同时选取，允许某种为零。底部实时汇总：“收到：羊 ×2、矿 ×1”；下一步进入给出选择。

不要根据对方隐藏的资源种类设置上限或提示“对方有多少矿”。数量上限必须沿用现有规则/协议的合法约束；如果没有适合滑条的较小上限，使用可扩展范围或同步数字输入，不任意新增 10 张等业务上限。原型可使用明确标注的展示范围，须留出输入更大合法数量的方式。

### 2.3 第二步：我愿给出

沿用相同的 5 种资源卡和数量控件。给出上限依据自己当前拥有的各资源数量，显示“持有 N”。零资源项显示零且不可增加，仍保持五类资源位置稳定。

上方保留第一步的紧凑摘要和“修改”入口；底部显示双方完整条件，例如：

> 给乙：木 ×2 → 收到：矿 ×1

可以返回第一步修改，双方草稿都不丢失。此步直接发送，不再强制弹第三层确认框；双方条件和接收人必须在发送前完整可见。

发送中防重复操作。成功后显示“已向乙发出提议”，保留已发报价摘要及撤回入口；失败保留可修正草稿，不把服务端拒绝表现为成交成功。

### 2.4 赠予和边界

- 允许任意一侧为零，明确显示“仅赠予”或“仅索取”，不能强迫两边都选资源。
- 双方均为零不能发送。
- 切换步骤不重置数量，关闭后重新打开可保留本次草稿；跨回合、掷 7、权限变化、重连快照后须校正，不能自动发送。
- 自己资源减少时，标出不足并要求修正，不悄悄改变已展示的交易条件。
- 滑条必须按整数变化；数量、摘要和滑条值同步，键盘可操作，焦点可见。
- 不能仅以图标或颜色传达资源类型；保留名称。

### 2.5 收到报价不能被编辑器隐藏

编辑面板目前覆盖原有报价区；10 秒有效期下，玩家容易错过别人提议。

建议顶部提供“发起交易 / 收到的提议（N）”切换，收到新报价时更新数量和轻提示，不自动抢焦点。切换回来保留草稿。不要把两套完整界面硬挤在一起。

收到报价卡统一以玩家视角表达“你给出 / 你收到”，不让玩家先判断提议者视角。列出对象、资源和剩余时间，按稳定顺序展示，可任选处理。

必须保持：每人最多一条有效报价、有效期 10 秒、发送冷却 3 秒、重发替换本人旧报价、按 offerId 接受、不预占资源、服务端成交时复核。掷 7、回合结束和游戏结束清空报价。不得为配合动画延长有效期或自动续期。

原型可模拟倒计时与冷却以验证交互，但清楚标记为本地模拟；不能伪称真实多人交易已接入。

## 3. 保留并落实上一轮界面评审

| 优先级 | 问题 | 本轮处理 |
|---|---|---|
| 高 | 辅助文字偏小、偏淡 | 提高玩家摘要、报价内容、数量和关键状态的可读性；主要操作文字建议 14–16px，不靠缩字解决布局 |
| 高 | 交易表单密集 | 按第 2 节改为两步图形编辑；减少大段规则说明 |
| 高 | 编辑交易遮住报价 | 提供带数量的切换入口；草稿保留、到达不抢焦点 |
| 中 | 接受与掷骰都使用大面积金色 | 建立主次按钮层级；保留明确可点击性，不让多个主按钮争抢视线 |
| 中 | 弃牌的“2”和“−1”含义不直观 | 明确显示“持有 2 / 已选 1”；取消一张的入口可发现，不仅依赖角标猜测 |
| 中 | 道路、建筑融入同色地形 | 加强轮廓和描边，特别检查黄色道路与麦田；用密集建筑状态验证 |
| 中 | 常态任务区像教程 | 收起长期说明，保留“你的回合·尚未掷骰”等即时任务；帮助入口提供完整规则 |
| 中 | UI 出现技术术语 | “服务端复核”改为“成交时双方须有足够资源”；技术细节留在文档 |

不得为增大文字而裁掉港口、遮住底部操作或引入普通对局的整页滚动。只针对桌面 1280×720 与 1440×900 优化，暂不扩展手机适配。

## 4. 动效：先做收益高、成本可控的部分

### 4.1 难度判断

短暂的骰子翻滚、卡牌抽出/翻面、按钮反馈、数字变化，通常可以用现有 DOM/SVG 配合 transform、opacity 实现，适合本轮。真实骰子碰撞、自由翻飞的 3D 卡牌、大量粒子与持续海浪模拟成本更高，本轮不做。

这里按“抽发展卡、强盗抽资源牌”理解用户提到的抽卡动效；玩家交易本身是报价和资源转移，不新增一种可抽取的“交易卡”玩法。

### 4.2 建议实施清单

| 优先级 | 动效 | 建议时长 | 目的 |
|---|---|---|---|
| 必做 | 按钮按下、卡牌选中、数量变化 | 100–180ms | 让操作有触感，不影响连续点按 |
| 必做 | 交易步骤切换 | 160–220ms | 保持面板位置稳定，突出正在编辑哪一侧 |
| 必做 | 掷骰短翻滚/抖动后显示结果 | 450–700ms | 提供掷骰仪式感，最终点数与权威结果一致 |
| 建议 | 购买发展卡从牌堆抽出，进入手牌 | 300–450ms | 说明新卡去了哪里 |
| 建议 | 成交后资源图标短距离移动或数量脉冲 | 250–400ms | 表达收付，不用跨屏飞满卡牌 |
| 建议 | 建筑确认后轻落下 | 160–250ms | 区分本地预览和真正落子 |
| 后续 | 强盗抽牌的背面卡移动 | 300–450ms | 表达随机抽取，避免泄露别人手牌 |

先完成必做项与一种抽卡效果，效果一致再扩展。不能为了增加动效新引入庞大依赖。

### 4.3 游戏正确性高于动画

- 正式游戏结果来自服务端，动画只表现结果，不能随机生成最终骰点、卡牌或成交内容。
- 收到真实结果立即更新逻辑；动画不得延迟弃牌锁、报价作废、结束状态等关键变化。
- 请求未返回时显示短暂等待，不伪造成功、不无限翻滚；失败结束等待并给出明确反馈。
- 以事件 ID 或已有去重机制保证一次动作只播放一次；重连快照不补播整局历史动画。
- 隐藏页恢复后直接展示最新状态，不排队播放积压效果。
- 动画不截获棋盘点击，不引发整页布局跳动；只对本次请求防重复，不锁住无关合法操作。
- 尊重 prefers-reduced-motion，减少动态时用直接更新和轻淡入；关闭动效仍能读懂所有结果。
- 卡背可公开，隐藏资源种类与发展卡内容只展示给有权知道的人。不能靠翻面动画提前泄漏。

## 5. 实施顺序与验收

1. 核对原型源码和现有交付规范，保护未提交文件；列出计划修改范围。
2. 完成两步交易流程，先验证数量选择、返回、赠予、草稿保留、报价切换。
3. 调整文字、按钮主次、弃牌反馈、道路轮廓。
4. 添加轻量动效，验证正常、失败、连续操作和减少动态模式。
5. 更新状态演示页、设计规范与资产清单，提交截图及验收记录。

交付至少包括：普通对局、交易第一步、第二步、收到报价、弃牌的两个尺寸截图；动效可运行预览（截图不能证明动效）；改动文件列表；模拟与未实现边界。

验收重点：

- 在 1280×720、1440×900 能读清数量，关键操作不溢出，普通对局不滚动整页。
- 三种以上资源混合交易、零数量、赠予、最大合法数量、返回修改均正确。
- 键盘和点按可以替代拖动，滑条整数与摘要一致。
- 编辑过程中收到新提议可发现；切换不丢草稿，过期报价不能被误接受。
- 动效开启/减少两种模式都能完成同样的操作，不影响时限和阶段边界。
- 原型无新增控制台异常；不宣称已经完成正式多人功能和移动端适配。
