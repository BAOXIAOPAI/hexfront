# 移动端为主力，要不要针对性重构

> 2026-11-06 · 纯评估。**本轮未修改任何代码，未改动其他任何文件。**
>
> 本轮输入的四个决定：视觉肯定要重构 / 主力设备是移动端 / 银行与港口不做拖拽 / 掷 7 不严格锁。
>
> 本文只回答最关心的那个问题：如果主力是移动端，这个项目是不是要针对性重构，以及「换」到底该换什么。

---

## 0. 结论

**要重构，而且是针对性重构；但不需要换项目、不需要换框架、不需要动后三层。**

两句话说明：

- 瓶颈不在技术栈，而在两个硬事实：**19 格棋盘 54 个顶点 vs 手指最小可点区域**，以及**每条 STATE 整块重绘 SVG vs 双指缩放/长按拖拽**。原生 TS 零框架不是劣势（前端包 54 KB），换 React、换小程序都解决不了这两件事。
- 现有 `@media (max-width: 900px)` 那套不算适配，是把桌面三栏砍掉一半：隐藏左右面板、手牌 `fixed` 到屏幕底部、棋盘整体缩小。继续往上叠补丁只会越叠越乱，应该删掉重写，而不是修补。

重构范围局限在 `apps/web`。规则引擎、消息协议、服务端房间与广播、248 个测试全部不动——它们都不认识屏幕尺寸。

---

## 1. 把「换」拆开，逐个判断

你说「如果本项目本身就不适合做移动端适配，可能需要换」。这里至少有五种不同的「换」，结论并不一样：

| 换什么 | 判断 |
|---|---|
| 换主力设备，退回桌面优先 | 不需要。技术上是可行的，只是要按手机重新设计交互 |
| 换前端框架（React / Flutter / 小程序） | 不解决核心矛盾。热区精度和手势冲突与框架无关；小程序还有游戏类版号问题（11-05 已确认）。原生 TS 反而更轻 |
| 换渲染方式（SVG → Canvas / WebGL） | 暂不需要。先把「整块重绘」改成骨架 + 增量更新就能解掉手势冲突；真遇到低端机掉帧再评估 |
| 换游戏内容（更小地图 / 更少顶点 / 异步回合） | **唯一可能需要认真谈的「换」**。见第 5 节，取决于你要的「手机玩」是哪一种 |
| 换整个项目推倒重来 | 不建议。规则引擎 + 248 个测试 + 已跑通的服务端是全项目最值钱的部分，且与屏幕无关 |

一句话：**该换的是 `apps/web` 的交互与布局，不是这个项目。**

---

## 2. 移动端真正的矛盾（按硬度排序）

### 2.1 棋盘密度 × 触屏精度（最硬，物理约束）

19 格地图有 54 个顶点、72 条边。手机宽约 390 CSS px，整岛按宽度缩放后，相邻顶点间距只有三十几 px；现有热区是半径 12.5 的 SVG 圆，缩放后直径约十几 px。而触屏可点目标的通行下限是 44×44 CSS px（Apple）/ 48 dp（Android）。**差着数倍，不是调 CSS 能补的。**

结论：必须提供缩放 + 平移（或放大镜式局部视图）；热区尺寸要按屏幕像素固定，不能随 SVG 一起缩小；落点要有二次确认防误触。这会同时影响摆位、建造、强盗三套交互的共同底座。

### 2.2 整块重绘打断手势

`scene.ts` 每收到一条 STATE 就 `svg.innerHTML = ...` 整块替换。桌面无所谓；手机上一条广播就能把正在进行的 pinch / pan / 长按拖拽的 DOM 抽掉，手势直接断。多人局广播频繁时更明显，低端机还会掉帧。

结论：棋盘骨架、静态层、热区层要拆开，只做增量更新；视图快照留在内存里，不靠 DOM 承载手势状态。

### 2.3 三栏信息架构没有空间

桌面是 `238px | 棋盘 | 262px` 加顶栏底栏。手机竖屏只有一列。现在靠「隐藏」处理，等于把玩家信息、发展卡张数、最近动作全砍掉——而这些在变体博弈里恰恰是决策依据（手牌 ≥8 警示、别人发展卡数量、「恶意投 7」的判断来源）。

结论：不是删信息，是分层。棋盘主视图 + 底部 sheet（手牌/建造/交易/结算）+ 顶部可拉取的玩家条。

### 2.4 输入模型整套要换

hover 说明在触屏不存在（现在 `@media (hover:none)` 直接隐藏，等于新手在手机上完全看不到成本说明）；点击要变长按 + 拖拽；`touch-action` 要显式声明，否则双指缩放会和页面滚动打架；鼠标与触屏要用 Pointer Events 统一；iOS Safari 要处理 `dvh` 与安全区 `env(safe-area-inset-*)`；相邻热区要有防误触确认。

顺带一个现实问题：说明文字（建造成本、发展卡牌面）在手机上没有 hover 可用，得换成长按或常驻的「?」，这属于视觉重构的一部分。

### 2.5 手机 + 语音 + 后台挂起

`03-trade-and-ux.md` 3.5 节早就预警过：切到语音 App，浏览器被挂起甚至标签页被杀，WS 断连。现有「同名重连 + 服务端整局保座」能接回来，身份也写在 URL 上，这点设计是对的。但标签页被杀时，本地的半截选择会丢——好在现在所有半截状态都能从 `view` 重新推导，这条要守住，不要为了移动端方便把状态挪进前端内存。

这条严格说不是 bug，是产品前提：**要不要接受边打边切语音的节奏**（第 5 节）。

### 2.6 全是 px 定值

顶栏 62/50、底栏 72/52、手牌固定 144、面板 240~272 宽、卡片 62×80。横屏、折叠屏、小屏都会挤。视觉重构时统一换成相对单位 + 断点，别再写死。

## 3. 保留 / 改造 / 重写清单

| 模块 | 处理 | 理由 |
|---|---|---|
| `packages/engine` | **原样保留** | 纯规则函数，与屏幕无关；248 个测试里大部分钉的是它 |
| `packages/protocol` | **原样保留** | 消息契约，前后端共用 |
| `apps/server` | **原样保留** | 房间、WS、按座位裁剪广播 |
| 前端纯函数层 `geometry / placement / build / robber / format / theme` | **原样复用** | 无 DOM 依赖，可单测，是候选位与文案的唯一来源 |
| `apps/web/src/net.ts` | 小改 | 补切后台/重连后的视图恢复，其余不动 |
| `apps/web/src/scene.ts` | **重写** | 全量 innerHTML 重绘、热区随 SVG 缩放、无缩放平移能力 |
| `apps/web/src/ui.ts` | **重写** | 近千行桌面 DOM 拼装与事件，绑定死三栏布局 |
| `apps/web/src/styles.css` | **重写** | 1700 余行，桌面 grid + px 定值 + 媒体查询补丁叠出来的 |
| `apps/web/index.html` | **重写** | 改单栏结构 |
| `tips.ts` / `decor.ts` | 改造 | tooltip → 长按/「?」；地形插画 SVG 可复用 |

粗估 `apps/web` 约七成代码要重写。但后三层与全部测试不动，这是「重构损失可控」的实质——**代价主要在写前端，不在担心里面的规则闭环被带坏**。

---

## 4. 护栏：怎么保证不把已验证的东西改坏

你说不用怕重构损失，AI 写代码。代码量确实不是问题；真正要防的是「改来改去把已闭环的规则带坏」。四条硬约束：

1. **硬边界**：不碰 `packages/engine`、`packages/protocol`、`apps/server`，不改任何现有测试。规则闭环是纯函数 + 测试钉死的，与屏幕无关，没有理由动。
2. **一次一个模块**：重写 `scene.ts` 就立刻跑全量测试，绿了再动 `ui.ts`。不要大爆炸式一次性替换。
3. **状态仍然只在服务端**：移动端为了流畅很容易想「前端先乐观更新」，这条会推翻项目铁律，也会让断线重连出现幽灵状态。守住「一切变更走 COMMAND → 服务端裁决 → 广播」。
4. **验收必须真机或用正确视口**：之前踩过 headless Chrome 的坑（`--window-size=390,844` 实际按 756px 布局再缩放，导致误判「移动端被裁切」）。至少覆盖摆位、掷 7 结算、建造、交易四种触屏手势，不能只靠截图看外观。

另外：视觉重构与交互重构并行时，**先定布局骨架再换皮**，否则两边互相返工。

## 5. 仍然要你定的两个产品前提（这两个不是技术问题）

### 5.1 你要的「手机玩」是哪一种

| | 场景 | 对地图的影响 |
|---|---|---|
| **A** | 聚会时手机代替电脑，能看全盘、能操作，允许双手 + 缩放 | 19 格 / 54 顶点可以保留，按第 2 节改造即可 |
| **B** | 地铁上单手随手玩一局 | 54 个顶点先天别扭，需要简化地图、减少顶点，甚至改成异步回合——**这才是真正需要「换」的地方** |

我判断你要的是 A。如果其实是 B，本文结论要改：那就不是重构前端，而是重新设计游戏规格。

### 5.2 语音谈判怎么放

V-7 定的是「口头支票靠语音，系统不介入、不保障、允许毁约」。手机主力下，语音会打断游戏。要么接受这个节奏（靠重连兜住），要么补一个极轻的意向表达——但 `03-trade-and-ux` 明确砍过竞价看板和议价 UI，别走回头路。
