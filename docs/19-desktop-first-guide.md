# 六角拓荒：桌面优先建设与 AI 实施指南

> 日期：2026-11-10。本文是后续建设计划，不代表功能已经实现。
> 本轮仅编写指南，不修改应用代码、不部署，也没有重新运行应用测试。
> 读者：接手开发、设计和验收的 AI。目标：在现有项目上完成一版好看、好懂、可完整游玩的桌面网页。

## 1. 本次方向调整

**先做好桌面网页的完整体验，再评估平板，最后决定手机如何支持。** 当前不把平板、手机作为布局和发布验收目标，不再让手机横屏、浏览器旋转和软键盘问题主导开发。

这是一项范围调整，不是推倒重做。已经完成的多人同步、规则、报价队列、弃牌、强盗、棋盘选择、断线恢复继续复用。手机专项工作暂停；通用能力保留。

本阶段的成功标准：玩家打开网页，能明确看到棋盘、手牌、对手和轮次；能自然完成建造与谈判；画面体现温暖的海岛桌游，而不是开发工具或堆满按钮的后台。

### 1.1 已确认的决定与实施默认值

| 类别 | 内容 |
|---|---|
| 用户方向 | 桌面先行，先改善视觉和交互，移动端后续再做 |
| 已确认美术 | 海洋岛屿 + 精致插画桌游；温暖、清晰，有实体棋子和卡牌质感 |
| 已确认社交 | 朋友约好一起玩；游戏不提供语音，使用外部电话或语音房 |
| 本指南建议默认值 | 桌面最低支持视口 1280×720 CSS px；主要设计视口 1440×900；同时检查 1366×768、1920×1080 |
| 本指南建议默认值 | 首轮验收桌面 Chrome、Edge；macOS Safari 单独记录兼容结果，未测不宣称支持 |
| 后续再定 | 平板的具体设备、手机是否完整对局、PWA、安装体验、下一阶段浏览器支持范围 |

默认值用于让开发直接开始，不是用户已经逐项确认的承诺。若实测证明最低尺寸不够，应先调整信息层级；不要偷偷把最低尺寸抬高到只适合大显示器。

### 1.2 本轮不做

- 手机完整对局、竖横屏切换、CSS 整页旋转、系统方向锁和手机软键盘专项适配。
- 平板专项布局、真机触控验收、PWA、原生 App、小程序。
- 5–6 人扩展、新规则、游戏内语音、账号体系、匹配大厅、观战系统。
- React/Vue 迁移、Canvas/WebGL 重写、后端或云平台迁移。
- 为视觉重构重做已验证的协议和规则。

## 3. 必须保留的规则契约

视觉改造前后以下行为必须一致，不得换成“标准卡坦”的默认理解。

| 场景 | 必须保持的行为 |
|---|---|
| 掷骰时机 | 回合内可先建造、交易、打发展卡；未掷骰不能结束回合 |
| 报价权限 | 当前玩家可向其他玩家报价；非当前玩家只能向当前玩家报价 |
| 报价并存 | 每人最多 1 条有效报价，全桌多条并存；按时间排列，可任选处理 |
| 时限与冷却 | 有效期 10 秒，发送后冷却 3 秒；重发替换本人的旧报价，新 ID 重新计时；不自动续期 |
| 接受报价 | 按 offerId 操作；服务端验证时效、权限、双方资源；报价不预占资源 |
| 报价作废 | 掷 7、回合结束、游戏结束清空；不得在后续恢复旧报价 |
| 弃牌 | 8 张起弃一半向上取整，系统算张数，玩家自己选择资源；不随机代弃 |
| 尚有人弃牌 | 暂停建造、玩家交易、银行/港口兑换、发展卡，仅允许应弃牌者提交弃牌 |
| 弃完但强盗未完成 | 恢复建造、交易、兑换；发展卡与结束回合仍禁用，直到强盗结算完成 |
| 银行/港口 | 点击选资源与确认，不要求拖拽；无限银行；借港按现有当前玩家代执行流程 |
| 信任交易 | 不新增自动租金、债务执行或口头承诺担保 |
| 多人同步 | 服务端决定资源、建筑、报价与阶段；本地只管理草稿、选中、相机和等待反馈 |

不要为了某个面板“更简单”，额外锁住弃完牌后的所有行动。也不要因为外部语音存在而省略报价内容、交易对象与确认结果。

## 4. 桌面信息架构

### 4.1 对局主画面

使用一个稳定的游戏桌面：顶部对手与轮次、中间棋盘、右侧上下文区、底部自己的手牌和主要行动。

```text
┌──────────────────────────────────────────────────────────┐
│ 房间/连接   玩家甲   玩家乙   玩家丙   玩家丁   当前回合  │
├──────────────────────────────────────────┬───────────────┤
│                                          │ 当前任务      │
│               海洋与岛屿棋盘             │ 或操作面板    │
│                                          │               │
│   缩放/复位                  最近结果提示 │ 报价提醒/入口 │
├──────────────────────────────────────────┴───────────────┤
│ 我的资源卡 / 发展卡     建造   交易/兑换   掷骰   结束回合 │
└──────────────────────────────────────────────────────────┘
```

这是信息布局示意，不是要求照着画矩形边框。海面贯穿背景，玩家条、手牌架、任务区作为轻量桌游部件。

建议初始尺寸：顶部约 64–80px、底部约 112–144px、右侧约 280–320px，其余空间给棋盘。使用 Grid/Flex 和合理上下限，具体值以 1280×720 实测修正。棋盘居中于自己的可用区域，不是整个浏览器。

- 正常对局不滚动整个页面；仅报价列表、日志、较长任务内容可局部滚动。
- 棋盘默认能看清全岛和港口；不能为了装饰裁掉可操作边缘。
- 当前回合、是否掷骰、需要自己做什么，不能只依赖日志。
- 右侧同一时刻展示一个主要任务，不同时展开所有建造、发展卡、兑换表单。
- 执行强盗或建造时，右侧说明步骤，棋盘继续可操作；避免全屏遮罩挡住目标。
- 报价到达不抢焦点、不关闭当前草稿，不强行把人带出建造流程。
- 日志默认收起或只显示最近摘要，随时可打开查证；不要把它占成第二条常驻宽侧栏。
- 最低支持尺寸仍须露出手牌、关键按钮和当前任务，不靠全屏模式才能操作。

### 4.2 入房、等待与结束

入房页直接提供昵称、房间信息和进入按钮，配少量同风格岛屿画面。不要先做营销首页、宣传卡片和无关功能列表。

等待页以玩家座位为主体，清楚展示谁已加入、谁能开始、当前等待原因；只暴露后端已有权限。保留邀请/复制入口时提供成功或失败反馈。

结算页沿用实际可见信息展示获胜者、分数和本局结果，提供现有的回房流程。不得伪造尚未实现的对局统计或“再来一局”能力。

### 4.3 小窗口处理

按可用 CSS 视口判断，不按手机 UA 一刀切；桌面浏览器缩放也会影响可用空间。低于当前最低范围时可提示“当前窗口较小，建议使用电脑并扩大窗口”，不得自动旋转整页或强制全屏。

对局中缩小窗口不能清空身份、退出房间或丢失快照。必要时用可恢复的尺寸提示遮挡操作，窗口恢复后回到当前状态；网络恢复机制继续运行。此阶段不因平板偶然显示正常就宣称已完成平板支持。

## 5. 视觉设计规格

### 5.1 核心画面

设计成“晴暖海面上的一张实体岛屿桌游”。岛屿是视觉主角；资源牌与木质棋子提供触感；文字和按钮保持清晰。避免厚重木纹铺满背景、玻璃面板覆盖棋盘、强烈发光和过多持续动画。

建议色彩起点（可在视觉样板阶段调整，并非必须逐值照抄）：海面 `#276D7C`、浅海 `#6BAFA8`、纸面 `#F4E8CE`、主文字 `#342A22`、强调金 `#C99745`。把它们定义为语义变量，不在各文件重复硬编码。玩家颜色与资源颜色分别管理。

正文优先清晰的中文字体和可靠回退；标题可少量采用有桌游气质的字体。正文通常 14–16px，小型标签不靠压到极小字号节省空间；必须校验实际背景上的对比度。引入字体须考虑授权、加载大小和失败回退。

### 5.2 资产清单与约束

| 资产 | 要求 |
|---|---|
| 6 类地形 | 森林、丘陵、牧场、田地、山地、沙漠；统一光向、透视和颗粒感；中心数字区域保持干净 |
| 5 类资源图标 | 与地形对应，缩到手牌和报价尺寸仍可辨认；图标旁保留数量与必要名称 |
| 路、村、城 | 同一套实体棋子语言；轮廓清楚，城市不能只是村庄变大一点；玩家颜色可区分 |
| 强盗、港口、数字圆片 | 位置信息清晰，强盗不挡住必须读到的数字；概率提示沿用规则 |
| 发展卡 | 统一卡框与背面，不同类型有明确标题、图标与说明；数量增加不无限挤占桌面 |
| 骰子与小图标 | 风格统一；信息不依赖 emoji 或平台不同的符号外观 |
| 海面与纸面纹理 | 低对比、可压缩，不干扰棋盘命中，不叠加大量昂贵滤镜 |

优先复用已有合适资产。需要补图时先做一组样板，再批量扩展；不直接拿官方商业美术或不明来源图片。生成资产记录来源、生成说明和用途；禁止把动态文字、资源数量烘焙进图片。棋盘地形可用插画，轮廓与命中继续由现有 SVG/几何控制。

建议将新资产放在项目现有公共资源约定下的独立目录，并创建清单。清单至少含文件、用途、尺寸、透明背景要求、来源/授权、回退方式。导出完成后本地加载，不能依赖临时外部图片地址。

### 5.3 控件与反馈

- 手牌以 5 类资源的卡片堆叠/数量呈现，不按每一张资源铺开；发展卡单独入口或小手牌组。
- 公共玩家摘要显示允许公开的信息；不能为丰富画面泄漏别人的资源种类、隐藏胜利点或发展卡内容。
- 只有当前最重要的动作采用强强调；“结束回合”位置固定，与“掷骰”明确区分。
- 禁用动作给出可见或可点击读取的原因，例如“还需移动强盗”；不能仅变灰且靠 hover 才解释。
- 焦点、选中、合法落点、危险操作分别有样式；玩家身份除颜色外有名字/标记，不能仅凭红绿辨认。
- 点击后短反馈，等待服务端时防重复提交；失败保留可修正草稿并显示原因。
- 资源变化、掷骰结果、建造落下可做短动画；不阻塞规则推进，支持减少动态效果。

## 6. 核心交互流程

| 流程 | 呈现与操作 | 必须验收 |
|---|---|---|
| 开局选地 | 显示当前步骤、剩余时间/规则；选位置→预览→确认，取消只取消当前选择 | 未提交的预览不当作真实建筑；超时/阶段切换后旧选择失效 |
| 建造 | 点建造类别→合法位置高亮→选点/边→成本与位置确认→提交 | 缩放后命中正确；资源变化后不能提交过期合法性；Esc 可取消草稿 |
| 资源手牌 | 随时看清自己 5 类数量，资源变化有轻提示 | 数量以服务端为准；长名称/大数量不挤掉操作 |
| 发报价 | 选择对象、给出与索取资源，展示双向内容与发送冷却 | 允许规则支持的赠予；不自行新增标准比例限制 |
| 收报价 | 稳定时间顺序显示对象、内容、剩余秒数，展开任意一条处理 | 接受针对明确 ID；过期/替换/资源不足都有准确反馈；新报价不让按钮突然换目标 |
| 银行/借港 | 在交易区内切换；选资源、比例、受益对象，预览净变化后确认 | 展示真实可用港口与权限；不采用拖拽；不自动扣租金 |
| 发展卡 | 打开手牌→选类型→说明与目标步骤→执行 | 去掉重复的“计数列表+同义按钮墙”；新买/本回合使用限制沿用引擎 |
| 掷 7 | 清空报价，要求弃牌者看到“已选/应弃”；其他人看到等待谁 | 不随机代弃，不接受旧报价；弃完后解除应解除的限制 |
| 强盗 | 持续显示待完成提示，棋盘选目标，再按规则选受害者 | 普通掷 7 和骑士流程都可完成；不能提前结束回合 |
| 重连 | 小范围连接状态，恢复中禁止重复发送，快照到达后校正 UI | 身份/座位沿用已有逻辑；过期草稿不自动提交；不重复执行已完成动作 |
| 结束 | 真实结果与回房入口 | 终局禁止继续行动，刷新/重连仍正确展示结果 |

对必须选择目标的操作使用明确的确认入口，别同时叠加三次确认。基础点击流程完整后，才加 hover 预览、快捷键、拖动等效率增强。快捷键不能在输入昵称、数量等文本时误触；Esc 不得退出房间或撤销已成交动作。

## 7. 代码调整与未来复用边界

### 7.1 分离职责，避免重写

保留现有栈：Vite + 原生 TypeScript + SVG + Node WebSocket。可以根据改动提取小模块，例如玩家条、手牌区、报价列表、任务面板；不要求先建立一个通用 UI 框架。

分清三层：

1. 规则/协议层：动作是否合法、资源如何变化、报价是否过期。
2. 通用交互层：选中目标、报价草稿、确认、取消、请求等待和恢复校正。
3. 布局/视觉层：组件摆放、宽度、图案、动画和设备专用呈现。

未来平板主要调整第 3 层，必要时调整触控交互。手机可能需要新的信息分组和任务呈现，不能承诺仅改几个媒体查询。现在保留第 1、2 层复用能力即可，不提前实现两套隐藏界面。

### 7.2 手机历史代码的处理

首先建立可运行桌面基线，再处理遗留代码，不能先删除一大批文件。

| 类型 | 本阶段处理 |
|---|---|
| 整页 CSS 旋转、方向锁、手机强制横屏提示 | 停止扩展；从桌面入口路径隔离，确保不会意外启动 |
| `panels.ts` 横屏状态与 `layout.css` 旋转覆盖 | 梳理调用和选择器依赖；必要时拆出遗留模块，逐项移除桌面耦合 |
| 相机、坐标换算、缩放复位、指针事件 | 保留通用部分，桌面改布局后重测命中；不要整份删除 `camera.ts` |
| 重连、后台恢复、快照校正、错误反馈 | 保留；桌面也会切出浏览器、休眠和断网 |
| 手机专用测试与报告 | 保留历史证据；功能明确退出范围时可归档专项用例，注明理由，不伪装成 PASS |
| 通用规则、同步、面板生命周期测试 | 继续作为回归要求；不能因文件名含 phase-d 就整组跳过 |

如果暂时保留一段不干扰桌面的手机逻辑比删除更稳，允许保留并记录。清理量不是完成度。不得为了过测试把真实行为断言改成“元素存在”或仅匹配源码字符串。

## 8. 分阶段实施与交付物

以下使用 `PC-0` 至 `PC-5` 命名，避免与历史 A–D 和旧 E/F 计划混淆。按阶段交付；不要一次性重写全部界面后才给用户看。

### PC-0：范围收口与基线

任务：读取必读文档；检查工作区；启动当前项目；截取当前桌面对局/等待/交易画面；核对支持尺寸和当前测试结果；列明桌面代码与手机专项依赖。

交付：简短基线记录，包含分支/提交及未提交文件摘要、运行命令、实际测试结果、截图、已知问题、计划修改文件。大文件只列职责与计划，不因行数多就全部拆分。

通过条件：当前状态可恢复，开发者能说明哪些成果必须保留；测试既有失败与新失败可区分。无法运行时明确阻塞，不能用旧截图冒充现状。

### PC-1：可运行的桌面布局

任务：在现有页面实现顶部玩家、主棋盘、底部手牌与行动、右侧上下文区；接入真实状态与现有动作；隔离桌面旋转路径。此步以布局、信息层级为主，不批量制作美术。

交付：1280×720、1440×900 的对局截图；建造、报价、弃牌三个主要任务的可运行页面；改动说明。

通过条件：最低视口不遮挡核心控件；所有旧功能仍有入口；无明显重复操作墙；改变窗口大小后棋盘与命中正确。不能以静态设计图代替可操作页面。

### PC-2：完整视觉样板

任务：做一套统一地形、棋子、资源、卡牌与按钮样板，应用到一个有代表性的真实对局状态。包括资源充足、建筑较多、存在报价和发展卡的状态，不只展示空棋盘。

交付：视觉变量、资产清单、真实页面截图；与 PC-0 同尺寸对照；加载失败的回退方案。建议此时向用户展示一次，再全面扩展，避免美术方向错误造成批量返工。

通过条件：海岛与实体桌游质感一致；正文、数字、落点仍清楚；交易与手牌比装饰更易读；没有占位图或乱码。是否需要额外停下来等待批准，以用户当次实施指令为准。

### PC-3：全部流程接入与状态完善

任务：按第 6 节覆盖入房、等待、开局、建造、报价、兑换、发展卡、弃牌、强盗、回合结束、断线恢复与终局。处理长昵称、零资源、富资源、报价并存和快速过期等边界。

交付：流程完成表，每项列实际入口、权限/禁用原因、异常反馈、证据；相关行为测试；保留规则契约的说明。

通过条件：不是只有主画面变好看；所有流程能完成，强制任务不会被普通面板覆盖，也不误锁被允许的操作；不会泄漏隐藏信息。

### PC-4：桌面验收与收尾

任务：运行必要检查、浏览器实测、完整对局；修复视觉溢出与交互问题；清理明确废弃的桌面依赖；更新状态文档。

交付：验收报告与截图，列 PASS / FAIL / BLOCKED / NOT_RUN；准确记录浏览器、版本、CSS 视口、测试方式、已知限制。不要将机器人对局等同于浏览器 UI 验收。

通过条件：第 9 节必须项完成；没有规则/同步回归、流程阻断、隐藏信息泄漏或支持尺寸内不可操作的问题。未完成项明确影响和去向，不宣称“全面兼容”。

### PC-5：下一阶段决策（不自动开始）

桌面稳定后，整理真实玩家体验反馈：是否看得清、是否知道轮到谁、交易是否及时、是否能顺畅完成一局。然后由用户决定发布、继续桌面打磨或启动平板。

平板阶段先复用桌面布局测试触控、点击说明、浏览器栏与后台恢复；手机阶段单独做小屏交互原型。不要在 PC-1 至 PC-4 中偷偷恢复手机专项范围。

## 9. 验收清单

### 9.1 自动检查

在仓库根目录运行已有命令：

```bash
pnpm typecheck
pnpm test
pnpm build
```

先检查依赖是否齐全，必要时按现有锁文件安装。构建可能更新受跟踪产物，交付时列明，不要手工修改 dist 修问题。依赖版本无必要不升级。

对改动增加有价值的行为测试：报价过期时不能点到另一条、阶段变化清理旧选择、弃完后恢复正确动作、快照后草稿校正。纯颜色和间距用浏览器检查，不为每个 CSS 值编写脆弱断言。

### 9.2 浏览器与视口

| 项目 | 要求 |
|---|---|
| Chrome | 1280×720、1366×768、1440×900、1920×1080 检查布局；1440×900 执行全部核心流程 |
| Edge | 最低支持尺寸与主要尺寸检查；至少覆盖入房、建造命中、报价、重连 |
| macOS Safari | 环境可用时检查 SVG、表单、布局与核心操作；否则记录 NOT_RUN，不能标 PASS |
| 窗口变化 | 对局中缩小再恢复，检查状态、相机、弹层位置和身份；浏览器缩放后按实际 CSS 视口判断支持范围 |
| 键盘与可读性 | Tab 焦点可见、确认/取消可达、文本框输入不触发快捷键；信息不只通过颜色/hover 给出 |

没有对应浏览器不能用 Chromium 改 UA 冒充。没有真机平板/手机不影响本次桌面专项验收，但也不能新增支持承诺。

### 9.3 功能必测

1. 多人入房、准备/开始及开局选地，实际身份与公开信息正确。
2. 掷骰前建造/交易仍可用；未掷骰不能结束回合。
3. 路、村、城的选择/取消/确认，缩放和平移后均命中正确。
4. 多报价并存、任意选择、10 秒失效、3 秒冷却、本人替换、旧 ID 拒绝、接受时资源不足。
5. 银行兑换、现有借港流程、赠予；校验双方资源结果。
6. 掷 7 清报价→各自选牌→弃完恢复部分动作→移动强盗→恢复发展卡/结束回合。
7. 各类可操作发展卡完整流程，包含骑士与修路；不可使用时显示原因。
8. 断线/刷新/重连后身份与状态恢复，旧选择/报价不误提交；服务端错误可理解且不反复刷屏。
9. 至少一局四个浏览器客户端参与的完整 UI 对局，从入房到终局再回房。可自动化点击，但不能用协议机器人替代 UI 链路；局部边界允许可复现测试种子辅助。
10. 控制台无新增未处理异常，资产无丢失；主要页面不溢出，长昵称、大数量、空列表和报价过期后布局稳定。

测试种子必须限定开发/测试环境，不得给生产端留下任意改资源接口。完整对局与边界种子各证明什么，应分别写清。

### 9.4 视觉证据最小集

保存同尺寸的入房、等待、普通对局、建造预览、报价列表/编辑、兑换、发展卡、弃牌、强盗、恢复提示和终局截图。普通对局至少覆盖最低与主要设计视口。截图应来自运行页面，注明状态和视口，不以设计稿证明实现完成。

## 10. 交付规范与范围控制

每个阶段报告：完成了什么、修改哪些文件、怎样验证、剩余哪些问题、下一阶段是什么。先报告用户看得到的结果，再列实现细节。

不要为“未来可能需要”建立设备插件系统、通用状态管理框架或两套全量页面。只有当具体问题已出现、当前结构妨碍解决时，才做必要拆分。

桌面优先不会让未来适配零成本：平板仍有触控、浏览器行为验证；手机可能需要重新组织布局。减少浪费的关键是先确定稳定的规则、组件和视觉语言，让后续设备复用这些成果，而不是现在维护三个尚未成熟的版本。

报价、弃牌、强盗和断线恢复。不要回滚阶段 D，不要照官方卡坦改变体规则。
