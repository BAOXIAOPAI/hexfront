# 17 通用横屏 UX 规格：CSS 自旋转 + 系统方向锁定渐进增强

## 0. 一页结论

| 项 | 结论 |
|---|---|
| 通用底座 | **CSS 自旋转**：竖屏视口内把完整横屏画布旋转 90° 铺满，零浏览器 API 依赖 |
| 渐进增强 | **系统方向锁定**：有能力且被允许时额外请求系统横屏，体验最好；失败/缺失/被拒无感回落到自旋转 |
| 用户体验目标 | 打开即是一张完整横屏棋盘，**不再弹卡片要求用户自己想办法转手机**；把手机物理横过来内容正好正着 |
| 唯一旋转方向 | `rotate(90deg)`（顺时针自转）→ 提示「把手机**向左**横过来」；见 §2.1 |
| 主提示文案 | 「把手机向左横过来，棋盘就正了」；见 §2.4 |
| 不干预阶段 | 入房、输入昵称/房间号、等待玩家：保持竖屏，避开软键盘；见 §1.2 |
| 出口 | 「仍按竖屏查看」→ 本次会话不再强制，且可从帮助/设置恢复；见 §4 |
| 与指南 4.2 | 不违反，是把「无法锁定时给出手动旋转提示」升级为「页面已替用户转好」；见 §8 |

**设计支柱（3 条，用于后续评审防漂移）**
1. **零依赖可用**：不装 Chrome、不装 PWA、不改系统设置、不点任何按钮，也能看到并可操作一张完整横屏棋盘。
2. **不打断对局**：进入/退出自转不发送游戏命令、不退出房间、不重连、不重建棋盘、不丢待确认选点（指南 4.2 第 3 条）。
3. **不反复打扰**：转向提示一次会话只出现一次，轻、可关、自动淡出；临时竖屏接电话回来仍能看见待处理任务（指南 4.2 第 5 条）。

## 1. 触发条件与阶段策略

### 1.1 「需要横过来」的三个判据（三者同时成立才干预）

| # | 判据 | 建议阈值 / 信号 | 说明 |
|---|---|---|---|
| V | **视口方向** | `(orientation: portrait)` 且短边 ≤ **700 CSS px** | 复用现有 `syncPortraitGate()` 的 `matchMedia('(orientation: portrait)') && innerWidth <= 700`（`panels.ts:611–613`）。**不得改用 `max-width:900px` 判断手机**——指南 §14.1 明确「大手机横屏可能超过旧的 900px」。 |
| D | **设备类** | 以视口为主判据；`pointer: coarse` 仅作辅助，不依赖 UA | 平板竖屏（短边约 ≥ 768 CSS px）与桌面**不进入**自转：它们本就有足够宽度（指南 §13.1 平板 1024×768 属布局过渡）。国产浏览器/微信内置对 `pointer` 的取值**需实机复核**，不得因取值异常把手机排除。 |
| P | **对局阶段** | 已进入对局（有 `PlayerView`）；见 §1.2 | 入房/等待阶段一律不干预。 |

> 三者是「与」关系：`V ∧ D ∧ P`。任一不成立即保持原生布局。另需排除系统**真的**处于横屏的情况（此时视口已是横屏，V 不成立），走 §3 的 S7。

### 1.2 阶段判定：软键盘硬约束

**要求**：输入昵称、房间号、选择房间、等待玩家全程保持竖屏原生布局，**不旋转、不尝试系统锁定、不弹任何转向提示**。

理由（不臆造能力，只陈述已确认的风险）：自转会把输入框一起转 90°，侧躺的输入框、中文候选栏与软键盘弹出后的 `visualViewport` 变化叠加，会让打字与光标定位不可用；iOS Safari 与国产内置浏览器在旋转容器内的软键盘表现**需实机复核**（对应 `docs/16` §4 D8「安全区 / 软键盘 / 内置浏览器」仍为 NOT_RUN）。**宁可入房阶段朴素竖屏，也不要为了统一而牺牲能不能进房间。**

阶段信号以**现有代码事实**为准，不要只看 `STATE`：

| 阶段 | 代码事实（`apps/web/src/main.ts`） | 自转策略 |
|---|---|---|
| 未入房 / 等待开局 | `view === null`，`LOBBY` 分支 `ui.showLobby(...)` 显示 `#overlay` / `#sheet`（`main.ts:157–165`）；`WELCOME` 且 `!msg.view` 同样 `showLobby`（`main.ts:152–154`） | **不干预**（S0） |
| 恢复快照直接带视图 | `WELCOME` 的 `msg.view` 存在 → `view = msg.view; ui.hideOverlay(); ui.render(view, [])`（`main.ts:147–151`） | **启用**（S1→S2） |
| 开局 / 摆位 / 对局 / 结束 | `STATE` → `view = msg.view; ui.hideOverlay(); ui.render(...)`（`main.ts:170–178`）；`view.phase ∈ { setup, play, ended }`（`ui.ts`） | **启用**（S1→S2） |
| 对局结束 → 回房间 | `#end-screen` 的「回到房间」（`index.html:169`） | 点「回到房间」**退出自转**，回到 S0 竖屏 |

> **一致性要点（交 engineering-lead）**：判据请落在「`view !== null` / 入房浮层是否隐藏」上，而不是「是否收到过 STATE」——恢复快照的 `WELCOME` 也会直接带 `msg.view`，只等 STATE 会漏掉重连恢复的玩家。

### 1.2.1 软键盘态的主行动（「加入」按钮）可达性

**实测数据**（ULS-03 真机，Android Edge 156，华为 `ADY_AL00`，372×668 CSS px / dpr 3.375，证据 `probe/phase-d-universal-landscape-device-evidence.json` 与复验矩阵 §5.5）：聚焦昵称框后 `visualViewport` 高 668 → **342**；`#f-name` rect y ≈ 277.6–319.2 **完整可见**、中文可输入、自转 `mode=off`（A-4a 通过）；「加入」按钮 rect y ≈ 402.5–444.2，在**聚焦昵称框那一刻**落在 `visualViewport` 之下。

**补验结论：A-4b 判 PASS，初判「必须先收键盘」不成立（已撤销该定性）**

- **硬件 Enter 可提交**：焦点在 `#f-name` 时 `adb shell input keyevent 66` → 表单提交，进入等待页「1 / 4 人在座」（`android-17-enter-submit.png` / `android-18-enter-joined.png`）。
- **纯软键盘也可提交**：Gboard 两个输入框的动作键均显示「下一步」（因 `enterkeyhint=null`）。第 1 次点「下一步」焦点移到 `#f-room`，**此时面板上移、「加入」按钮变为可见**（`android-21-room-keyboard.png`）；第 2 次点「下一步」直接提交成功（`android-23-softkey-joined.png`）。
- 因此 A-4b 的两条判定 **(a) CTA 可见可滚到**、**(b) 回车可提交** 都成立：本项从「缺陷」改判为「**可用，但缺引导**」，**不需要改布局、不需要滚动兜底**。

**唯一真缺口：没有 `enterkeyhint`，两个输入框都显示「下一步」，用户不知道按两次就能进房**

**建议（低成本、零布局风险，推荐直接做）**

1. `#f-name` 加 `enterkeyhint="next"`、`#f-room` 加 `enterkeyhint="go"`（或 `send`），让最后一个动作键显示「前往 / 完成」，与「加入」语义一致；`enterkeyhint` 在国产内置浏览器与其他输入法下的支持**需实机复核**（R4）。
2. 在 `hint` 或输入框下方补一句「输完按键盘上的『前往』即可加入」；不新增控件、不改尺寸。
3. **滚动兜底降为可选**：既然第 1 次「下一步」后 CTA 已进入可视区、两条提交路径都在，本轮不必做滚动。若日后要加，**作用对象必须是 `#overlay` 或新增滚动包裹层，不能只改 `.sheet`**——实测 `.sheet` 的 `scrollHeight == clientHeight == 373`，溢出在 `.overlay` 层（`position:fixed; inset:0; place-items:center`，`styles.css:725–735`），且 grid 居中需配合 `align-items:start` 才滚得动。
4. 仍**不做** CTA 吸附 `visualViewport` 底部：`visualViewport` 在 iOS Safari / 微信内置 / 华为 / 夸克差异大，且 iOS / 微信内置目前仍 BLOCKED，风险不划算。

> **未覆盖范围（按输入法粒度写，勿把「未测」当「已覆盖」）**
> - **已覆盖**：仅 **华为系统输入法**（`com.huawei.ohos.inputmethod` / LatinIME，动作键显示「下一步」）。**A-4b 的 PASS 只覆盖这一档，不得外推到第三方 IME。**
> - **BLOCKED（设备未安装，本轮不装）**：搜狗、百度、讯飞等第三方输入法。其动作键标签与提交行为未知，可能不显示「下一步 / 前往」，甚至不透出提交。
> - **BLOCKED（无设备）**：iOS Safari、微信内置浏览器。
>
> **判定规则（与 quality-lead 已确认口径）**
> - 上述 BLOCKED 档若测到「动作键可提交，但 CTA 仍被遮挡」→ 记 **PASS（依赖动作键）+ 体验缺陷**，不擅自升 FAIL，用第 2 步引导文案缓解。
> - 若测到「CTA 不可见 **且** 动作键也不提交」→ **FAIL（必修）**，立即启用第 3 步滚动兜底（作用对象 `#overlay` 或新增滚动包裹层）。

### 1.3 其他不触发 / 需退出的边界

- **平板竖屏、桌面、分屏多窗口**：不触发自转；分屏造成的异常宽高比（既非典型竖屏也非典型横屏）按保守路径保持原生布局，**需实机复核**。
- **对局结束界面**：`phase === 'ended'` 时保持自转，让结果页与「回到房间」按钮正立可读；点击「回到房间」才退出。**待用户拍板**：也可选择结束页直接退出自转，二者取一。
- **局内文本输入**：现有对局内基本是按钮/芯片选择（`#drawer`、确认条），`#set-setup-grant` 是开局前的 checkbox。若后续新增局内文本输入，该输入层必须置于**不参与旋转的层**，或输入期间临时退出自转。列为实现约束。
- **系统方向真的变横屏**：立即还原为原生横屏布局（S7），不再自转。

## 2. 旋转方向与转向提示

### 2.1 唯一方向：`rotate(90deg)`（顺时针自转 90°），配套「把手机向左横过来」

> 这是 **UX 规格常量**，用途是统一「转向提示箭头方向 / 文案方向词 / 验收截图朝向 / 安全区映射方向」。具体画布几何、`transform-origin` 与位移由 engineering-lead 决定，本文不规定写法。

**理由（均为设计层面，不依赖未验证的浏览器能力）**

1. **用户动作与提示必须一一对应**：自转生效而用户还没转手机时，画面是侧躺的；此时唯一能让他看懂的是一条**不参与旋转、竖屏正立**的提示。选定 `+90deg` 后箭头方向随之唯一确定（指向左 / 逆时针放平）。若改成 `-90deg`，箭头必须镜像，否则会把用户引导到画面倒着的一侧。
2. **只支持一个方向，不做「猜用户往哪转」**：系统方向被锁死时前端拿不到可靠的物理方向（见 §2.3），猜测会造成「一半人正着、一半人倒着」的更差结果。宁可要求按提示转一次。
3. **单一常量、可低成本翻转**：角度、箭头、文案方向词由同一常量派生。若实机复核发现多数用户反向转手机，只翻转这一处，状态机、阶段判定、出口、可访问性与验收条目全部不变。
4. **与「页面已替你转好」的叙事一致**：竖屏握持时内容顺时针倒下，用户逆时针（向左）把手机放平，两者正好抵消，动作与直觉一致。

> **待用户拍板 / 需实机复核**：「向左横过来（顶部朝左）」是否符合目标人群的自然转机习惯，尚无本项目实测数据（现有真机横屏证据 `docs/16` §1.3 是靠 `cmd window user-rotation lock 1` 强制旋转，不是用户物理转动）。建议先按 `+90deg` 落地，把「方向习惯」列入 A-13 实机复核；若结论相反，翻转常量即可。

### 2.2 原理：为什么「系统方向没变、用户物理横过来内容正好正着」

写给团队，也用于组织面向玩家的解释（玩家版见 §2.4 副句）：

1. 系统方向被锁死（或浏览器不给锁定）时，页面拿到的 CSS 视口**始终是竖屏尺寸**，不会触发 `orientationchange`，`screen.orientation` 也不变。
2. 页面不再请求系统「把屏幕转过来」，而是**自己在竖屏视口里把一张完整横屏画布预先旋转 90°**。竖屏握持时，用户看到的是侧躺的横屏棋盘。
3. 用户把手机物理横过来，屏幕整体跟着转了 90°，**正好抵消这 90° 预旋转**，于是内容在物理世界正立。
4. 因为系统方向没变，所以**不退出房间、不重连、不重画棋盘、不丢待确认选点**（指南 4.2 第 3 条）；浏览器照常做 CSS transform 后的命中测试，看到哪里点哪里就中哪里——**此条必须由真机验证，见 A-3，不得由 CDP 截图代替**。

### 2.3 关键取舍：系统锁死时，前端无法知道用户到底转没转

系统方向不变 ⇒ 无 `orientationchange`、视口尺寸不变、`screen.orientation` 不变；`DeviceOrientation` 在 iOS 需用户授权且不适合作为常规依赖（**需实机复核**）。因此：

- **转向提示不能靠「检测到已横过来」自动消失**；
- 只能靠「**出现一次 → 自动淡出 → 可手动关闭 → 一次会话记忆**」收尾（§4）；
- 淡出后画面是干净的横屏画布，无常驻遮挡；
- 用户往**反方向**转手机会看到画面上下颠倒且提示已消失：需在提示副句里写清方向词，并在帮助里给一句「转反了就把手机转回来重来一次」；不新增第二个方向的自动适配。

这是本方案最主要的已知取舍，评审时不得被「应该能自动检测」的假设覆盖。

### 2.4 转向提示规格

| 项 | 规格 |
|---|---|
| 层级 | **不参与自转的独立覆盖层**，在竖屏坐标系里正立可读；不得放在旋转画布内（否则用户还没转手机时提示文字也是侧躺的） |
| 位置 | 贴**底部**居中细横条，避开顶部状态栏/刘海与底部手势条；用 `env(safe-area-inset-bottom)` 抬起。高度 ≤ **56 CSS px**，宽度 ≤ 视口短边 − 24 CSS px |
| 遮挡 | **不遮挡棋盘中心**：半透明底、贴边、不含模态、不拦截棋盘点击（提示条容器 `pointer-events:none`，仅其按钮可点）；不得出现覆盖全屏的卡片 |
| 内容 | **图形（手机轮廓 + 指向左的弧线箭头）+ 短文案 + 关闭按钮**。箭头是非文字信息，不依赖旋转后文字可读性 |
| 主文案（建议，待用户拍板） | **「把手机向左横过来，棋盘就正了」** |
| 副句（解释原理，避免困惑） | **「页面已替你转好，不用改手机设置，也不会退出房间。」** |
| 关闭按钮 | 「知道了」，`aria-label`＝「收起转向提示，本次不再显示」，触控目标 ≥ **44×44 CSS px** |
| 状态摘要 | 同层另给一行正立可读文字：「横屏棋盘已铺好 · 连接已同步 · 轮到 P1 · 待处理 1 条报价」，沿用 `#portrait-status` 的信息集（连接 / 当前回合 / 手牌分数 / 待处理）。**这条同时是可访问性补偿**，见 §5.2 |
| 语义 | `role="status" aria-live="polite"`；自转开启播报一次「已切换为横屏棋盘，把手机向左横过来即可正常操作」；同一文案不重复播 |
| 动效 | 出现时**不做入场动画**（避免与自转切换叠加闪烁）；约 **4–6 s** 后淡出，淡出时长 ≤ 约 **200 ms**（对齐指南 §9.3「普通交互反馈约 100 ms 内开始、结果动画约 1 s 内」）；减少动效时静态停留后直接移除，无淡入淡出、箭头不循环播放 |
| z-index | 需避开 `.overlay`(40) / `.drawer`(40) / `.portrait-gate`(45) / `.end-screen`(50) / `.toast`(60)；且不得与 `#setupbar` 顶部紧凑条重叠（`docs/16` §5 观察项 1 已记录 toast 与 setupbar 短暂重叠） |

> **与旧行为的差异（交 engineering-lead）**：现有 `#portrait-landscape`「进入横屏」主按钮 + 全屏卡片是**主路径**（`docs/16` §1.2），用户明确不想要「弹个卡片让人自己转」。新方案主路径是**无模态自转 + 轻提示条**；旧卡片不得再作为必须点按的关卡，可保留为「仍按竖屏查看」出口的宿主。

### 2.5 `screen.orientation.lock` 的用户手势约束（不违反「不弹卡片」的前提）

`docs/16` §1.2 已实测：`screen.orientation.lock('landscape')` **必须由用户手势触发**，多数浏览器还要求文档先进入全屏；iOS Safari 完全没有该 API，`requestFullscreen` 在 iPhone 上也基本不可用。因此：

- **不能在没有手势时静默发起锁定尝试**；
- 自转是**默认立即生效、零手势**的通用底座，进入对局阶段且 V∧D∧P 成立即生效；
- 系统锁定只作为**可选增强**，挂在两类手势之一：
  1. 顶栏/提示条上一个 **44×44 CSS px 的常驻可选方向入口**（不点也完全可玩，这是与「弹卡片」的本质区别：卡片不点就没法好好玩，入口不点照样玩）；
  2. 对局中**已有的一次用户手势**搭车尝试一次（transient activation 窗口内），**不得改变或消费该次点击的游戏语义**，也不得因锁定成功引发的 resize 丢掉待确认选点。
- 无论哪种，失败/被拒/不支持都**不再重试、不弹失败卡片**，保持自转；用户可随时通过可选入口手动重试一次。
- 锁定成功带来的收益表述为：系统按横屏渲染，视口与安全区按真实横屏计算，浏览器工具栏与画面方向一致，用户物理横过来后无需任何补偿。**具体表现因系统/浏览器而异，需实机复核**，不宣称能解决 `docs/16` §1.1 华为浏览器「中间竖条」问题。

| **S5 锁定失败 / 被拒 / 不支持 → 自转生效** | S3 的 `lock` reject / API 缺失 / 超时；或 S2 直接判定无 API（iPhone Safari、微信内置等） | **与 S2 完全一致**：自转继续或立即生效，画面不闪、不回退到退化竖屏 | 见 §6 三分支降级文案；**不重复弹转向提示**（若 `hintShown=1`）；播报文案只播一次 | 与 S2 相同；可选方向入口允许手动重试一次 | `hintShown` 不重置 |

### 3.2 迁移原则（防止支柱漂移）

- **S1 不得停留**：任何情况下都不能把「竖屏退化布局 + 一张卡片」当作稳定主态。
- **自转切换本身无过渡动画**：一次性瞬时完成，避免转场时内容侧躺/正立闪烁与眩晕；指南 §9.3 的动效预算只用于结果反馈，不用于自转切换。
- **S3 → S4/S5 不得影响点击语义**：搭车手势那一次点击仍按原样执行游戏操作；resize 不得重置相机、不得清除待确认选点（指南 §5.3 / §4.2 第 3 条）。
- **S7/S8 不消耗 `hintShown`、不改 `forced`**：来回切方向不应导致提示复活或用户的选择被推翻。
- **任何态都不发游戏命令、不退出房间、不重连**。

### 3.3 边缘情况（≥3 类，逐类给处理原则）

| # | 边缘情况 | 处理原则 |
|---|---|---|
| E1 | **软键盘还开着时收到 `STATE` 开局** | 阶段迁移先等输入框失焦/软键盘收起再进入 S2；不得在键盘弹出状态下旋转容器。若无法可靠检测，保守做法：本次不自动自转，等用户下一次主动手势再进入 S2，并在状态摘要里给「点一下铺成横屏」入口。**需实机复核** |
| E2 | **锁定 Promise 长时间 pending**（既不 resolve 也不 reject） | S3 设短时上限，超时按 S5 处理；不得让界面停在「尝试中」、不得禁用操作、不得反复重试 |
| E3 | **S6 之后系统方向又真变横屏 / 再变回竖屏** | 横屏照常显示原生横屏布局（S7，`forced` 不阻止系统给的方向）；再回竖屏回 S6，不重新强制、不弹提示 |
| E4 | **来电 / 切后台 / 标签被回收后回来** | 沿用指南 §10.2 与 §4.2 第 5 条：回来先核对权威状态，待处理任务在正立状态摘要里可见；不重放转向提示、不重置相机、不自动提交草稿 |
| E5 | **用户往反方向转手机 / 转了一半停住** | 不猜方向、不自动翻转；提示副句与帮助里给「转反了就把手机转回来，按箭头方向再来一次」；提示已淡出时可从帮助找回 |
| E6 | **对局结束 / 点「回到房间」** | 结束页保持自转（S2）正立可读；点「回到房间」退出自转回 S0 竖屏，避免回房输入时输入框侧躺 |
| E7 | **焦点落在某个按钮上时发生方向切换** | 焦点不得丢失，`:focus-visible` 的 3px 描边（`layout.css:89`）不得被旋转容器的 `overflow` 裁切；必要时把焦点移到不旋转层的等效控件并播报 |
| E8 | **分屏 / 折叠屏 / 异常宽高比** | 保守回退到原生布局，不强行自转；判据边界**需实机复核** |

## 4. 提示与出口

### 4.1 三类提示，互不叠加

| 类型 | 出现时机 | 形态 | 是否遮挡棋盘 | 是否可关 |
|---|---|---|---|---|
| 转向提示条（§2.4） | 一次会话首次进入 S2 | 底部细横条 + 图形箭头 + 短文案 | 否（贴边、半透明、不吃点击） | 是（「知道了」） |
| 降级说明（§6） | S5 | **并入转向提示条的副句或状态摘要的一行**，不另开卡片/弹窗 | 否 | 随提示条一起淡出 |
| 状态摘要 | S2 常驻（不旋转层） | 一行正立文字 | 否 | 否（但它很轻且是信息不是打扰） |

**禁止**：覆盖全屏的模态卡片、居中弹窗、遮罩、连续 toast、`#portrait-landscape` 那种「必须点才能玩」的主按钮、音效提示。

### 4.2 「仍按竖屏查看」出口

- 位置：转向提示条内（或提示淡出后收进帮助/设置），文案 **「仍按竖屏查看」**，触控目标 ≥ **44×44 CSS px**，键盘可达、焦点可见。
- 点击后：迁移到 S6，`forced=off`；退出自转、不再尝试锁定、不再弹转向提示。
- **S6 不是空白页**：必须保留连接状态、回合摘要、待处理任务、设置、帮助、恢复入口（指南 4.2 第 2 条）。
- 播报：「已回到竖屏查看」；toast 一次「已按竖屏查看，本次不再自动铺成横屏」（不反复）。

### 4.3 不反复弹出 / 一次会话记忆 / 是否可恢复

| 项 | 规格 |
|---|---|
| 提示次数 | 一次页面会话内转向提示**最多出现一次**（`hintShown`）；S5 回落、S7↔S8 来回切、resize / orientationchange 连发、切后台回来、临时接电话回来，均不得复活 |
| 记忆载体 | 会话内标志位，沿用现有 `portrait-gate.dataset.dismissed` 的思路（`panels.ts:187–191`）并扩展为「不再强制自转/锁定/提示」；**不写 localStorage、不跨刷新持久化**——刷新即视为新会话，重新出现一次（**待用户拍板**：若希望「同一天不再出现」需另立需求） |
| 可恢复 | **可恢复**。入口在帮助/设置内，文案 **「重新铺成横屏」**，≥44 px；点击后置 `forced=on`，从当前阶段重新走 S1→S2（若当时系统已是横屏则直接 S7），并允许重新显示一次转向提示 |
| 恢复后 | 不得重复叠加提示、不得重置游戏状态或相机 |
| 系统真横屏 | 与 `forced` 无关，始终正常显示原生横屏布局（S7）；`forced=off` 只约束「竖屏时是否强制」，不阻止系统给的方向 |

### 4.3.1 复活路径穷举清单（供验收与回归测试设计）

> 把「不得复活」落成**可逐条勾选**的清单。ULS-02c 曾修复一次「转向提示复活」（`dismissPortrait` 未封死、`resume` 回前台重新触发、`showHintStrip` 可被绕过、`syncHud` 残留 `fading`），说明只写原则在执行层容易漏分支。以下每条都须**单独**验证「不复活」，A-10 按此表逐项判定，不得只测其中一条。

| # | 可能让提示复活的路径 | 判定要求 |
|---|---|---|
| P1 | 用户点「知道了」收起提示 | 收起后**本会话不再出现**；定时器必须被清除，不得在淡出后又被任何重绘重新插入 |
| P2 | 用户点「仍按竖屏查看」（S6） | 同 P1，且不得因再回竖屏 / 再变横屏而恢复 |
| P3 | 每次收到 `STATE` 或任何 HUD 重绘（`syncHud` 一类） | 重绘不得重建提示 DOM、不得残留 `fading` 中间态；提示不因状态更新而重新出现 |
| P4 | 从后台回前台（`resume` / `visibilitychange`） | 回前台只做状态核对，**不得重新展示转向提示**——这是此前真实漏过的分支 |
| P5 | `resize` / `orientationchange` 连发（≥3 次） | 稳定停在「不显示」，不闪、不重复淡出 |
| P6 | S7↔S8 来回切（真横屏 ↔ 竖屏） | 提示不复活；`forced` / `hintShown` 不被方向切换改写 |
| P7 | 降级文案（S5） | 降级说明并入**既有**提示条，不得作为「第二次提示」重新弹出；不叠加 toast |
| P8 | 刷新页面 | **允许**再出现一次（新会话）；这是唯一允许复活的路径 |

> 实现层提示（非实现方案）：只用一个「是否展示过」的布尔位往往不够——需同时封住**定时器**、**重绘插入**、**回前台**、**淡出中间态**四个入口。ULS-02c 的修复方向（一次性封死 + 回前台再保险 + 渲染守卫 + 清理残留态）与本清单一致；验收请以 P1–P8 逐条回归，而不是只看「总共出现过几次」。

## 5. 可访问性

### 5.1 不靠颜色 / 动画 / 声音传递唯一信息

- 自转是否开启、锁定是否成功、是否降级，**都必须有可读文字**（状态摘要 / `aria-live` 播报），不得只用橙色块、高亮或旋转动画表示。
- 转向方向靠**文字方向词「向左」+ 图形箭头 + 手机轮廓**三重表达；箭头的弧线方向不得是唯一线索。
- 沿用指南 §4.3：拒绝原因、当前必须完成的任务不能只写在日志或只靠颜色。

### 5.2 `aria-live` 与阅读顺序

- 转向提示容器 `role="status" aria-live="polite"`（与现有 `#portrait-hint` `#toast` 一致）。
- 关键态变化各播一次可读文案：进入自转、回到竖屏查看、锁定成功。**S7/S8 方向来回变化不播报**，避免接电话回来刷屏；同一文案不重复播。
- **CSS 自转的固有风险**：`transform` 不改变 DOM 顺序与焦点顺序，但会让**视觉顺序与阅读/焦点顺序不一致**。缓解：
  1. 旋转画布容器给出明确 `aria-label`（如「横屏对局画布」）；
  2. 不旋转层保留**正立可读的状态摘要**（§2.4），屏幕阅读器用户不依赖视觉旋转即可获知连接、当前玩家、待办；
  3. 恢复入口与出口放在不旋转层，保证键盘可达顺序稳定。

### 5.3 焦点可见与 44 px 触控目标

- 沿用 `:focus-visible { outline: 3px solid var(--d-accent); outline-offset: 2px }`（`layout.css:89`）；自转后焦点圈必须仍可见、**不得被旋转容器 `overflow` 裁切**（E7）。
- 沿用 `--d-tap: 44px`（`layout.css:21`）。**自转容器不得整体 `scale`**：旋转是等距变换、不该改变尺寸，但一旦为了铺满引入缩放，44 CSS px 会缩水。验收 A-11 必须实测 `getBoundingClientRect()`，而不是只看 CSS 声明。
- 出口、恢复入口、「知道了」、可选方向入口全部 ≥ **44×44 CSS px**。

### 5.4 减少动效

- 同时覆盖 `@media (prefers-reduced-motion: reduce)` 与 `[data-reduce-motion="1"]`（`layout.css:394–395`，顶栏 `#btn-motion` 可切换）。
- 减少动效时：自转**瞬时切换**（本来就不该有过渡）、提示条静态停留后直接移除、箭头改为静态不循环、无淡入淡出；保留静态高亮与文字（指南 §9.3）。
- 两种开关都要在验收中覆盖，不能只测系统级 `prefers-reduced-motion`。

### 5.5 旋转后文字可读性

- **不因旋转额外缩小字号**：中文正文 ≥ **12 CSS px**，关键状态（连接、当前玩家、待办、确认）≥ **12 CSS px**；现状小横屏下 `.rail-title: 10px` / `.phase-flag: 10px` 已偏小，自转后不得再降。
- 对比度沿用 `--d-text #2f241b` / `--d-surface #fffaf1` / `--d-surface-2 #f3e8d5`，目标正文 ≥ **4.5:1**；**需实测，不宣称已达标**。
- iOS Safari 对 transform 后文字的亚像素渲染、国产浏览器的字体抗锯齿表现 **需实机复核**（A-11）。
- 提示条半透明底不得让下方棋盘数字透出来干扰阅读；必要时加不透明底衬。

## 6. 失败降级文案（面向普通玩家，无技术黑话）

### 6.1 原则

- **不出现**：`screen.orientation`、`lock`、全屏、API、方向锁定、WebView、方向请求、浏览器内核等词；不出现「不支持/被拒绝」这类带技术评判或责备感的措辞作为主句。
- **不假装成功**：不得只 toast「已切换到横屏」而实际没转。自转是真实可见的，所以「页面已替你铺好横屏棋盘」这句是真发生了的（对齐 `docs/16` §1.2「无静默失败、无假装成功」）。
- **替换旧文案**：`docs/16` §1.2/§1.3 的「浏览器没有允许切换方向，请手动把手机横过来，或检查系统的旋转锁定设置。」与「当前浏览器不支持自动横屏（iPhone Safari 常见），请手动把手机横过来」**必须替换**——新方案下用户不需要手动找方向、更不需要去改系统设置，旧文案会把人引到错误动作上。
- 降级说明**并入**转向提示条副句或状态摘要一行，不另开卡片、不叠加 toast。

### 6.2 三种情况

| 情况 | 前端能否区分 | 建议文案（待用户拍板） |
|---|---|---|
| **① 浏览器不支持**（`screen.orientation.lock` 缺失；iPhone Safari、微信内置、部分国产浏览器；`docs/16` §1.1/§1.2 已实测 iOS 无此 API） | **可区分**（API 缺失） | 「这个浏览器不能自动横屏，页面已替你铺好横屏棋盘；把手机向左横过来就能玩。」 |
| **② 浏览器拒绝**（有 API 但请求被拒；夸克 Android 12 / 华为 `ADY_AL00` 实测拒绝方向锁定，`docs/16` §1.3） | **可区分**（请求失败） | 「这个浏览器没允许切换方向，页面已替你铺好横屏棋盘；把手机向左横过来就能玩。」 |
| **③ 系统旋转锁定开着** | **无法可靠区分**：在多数实现里与 ② 表现相同（请求失败或静默无效），前端拿不到系统设置状态；`docs/16` §1.1 亦说明调试时需 ADB 查 `mCurrentRotation` 才能判断 | **统一文案**：「页面已替你铺好横屏棋盘，把手机向左横过来就能玩；不用改手机设置，也不会退出房间。」 |

> ③ 的统一文案同时也是**所有无法区分场景的兜底**，包括 ② ③ 混合、Promise 超时（E2）。「不用改手机设置」这句是刻意保留的：系统旋转锁定开着时，自转依然是可用路径，不该让用户去翻系统设置。
>
> **仅在帮助里**（不作为主提示、不主动弹）可补一句：「如果横过来后画面还是不对，可以检查手机的旋转锁定是否开着。」——面向少数确实遇到异常的用户，不打扰主流路径。

### 6.3 播报与出口

- 降级文案同属 `role="status" aria-live="polite"`，但**只播一次**；若 `hintShown=1`（例如 S8 之后再失败），不重复播报，只在状态摘要里保留文字。
- 降级态下「仍按竖屏查看」与「重新铺成横屏」入口始终可用。

## 8. 与指南 4.2 的关系

指南 `docs/10-refactor-guide.md` §4.2 原文四条：

1. 入房、输入昵称、选择房间、等待玩家均可正常完成 → 本方案 §1.2 **明确保持竖屏**并给出阶段信号，正面落实。
2. 开局后显示清晰的横屏建议，同时保留连接状态、回合摘要、设置与恢复入口 → 本方案 §2.4 的**状态摘要**与 §4.2 的 S6 出口逐项覆盖，且把「建议」升级为「已经铺好的横屏画布」。
3. 旋转不发游戏命令、不退出房间、不丢失待确认选择；重新计算可视区域 → §2.2 原理、§3.2 迁移原则、A-3/A-6/A-7 覆盖。
4. **「不把系统方向锁定或全屏 API 当成必要前提。无法锁定时给出手动旋转提示。」** → 这是本节要澄清的重点。
5. 若用户临时竖屏接电话，回来仍能看见待处理任务；不能无限重复弹出旋转提示 → §3.1 S8、§4.3、A-10 覆盖。

### 8.1 为什么不违反第 4 条

| 维度 | 指南 4.2 的要求 | 本方案 |
|---|---|---|
| 必要前提 | 不得是系统方向锁定 / 全屏 API | **必要前提改为「CSS `transform` 自转」**——纯 CSS，零浏览器 API 依赖，在 iOS Safari、华为、夸克、小米、微信内置等任何能渲染 CSS 的浏览器都成立。A-14 要求运行时禁用这两个 API 后自转仍完整可用 |
| 系统锁定 | 不作为前提 | 定位为**渐进增强的可选收益**：有能力、有手势、被允许时才请求，成功则取消自转（S4）；缺失/被拒/不支持一律无感回落（S5）。**有没有它，玩家都能玩** |
| 无法锁定时 | 给出手动旋转提示 | **升级而非取消**：原来只能请用户「自己想办法横屏」，现在页面已替用户完成旋转，提示从「请你转」变为「页面已铺好，把手机向左横过来即可」。信息更明确、动作更少、不再要求改系统设置（§6.1 替换旧文案） |

因此：本方案**没有把系统方向锁定或全屏 API 变成必要前提**，反而是第一条真正让「不依赖它们」落到可玩程度的方案。`docs/16` §1.2 的旧实现（主按钮 → 全屏 + `lock` → 失败则请用户手动旋转）恰恰在夸克 / iOS Safari 上退化成「只能竖屏看状态」，正是 4.2 想避免的局面。

### 8.2 与指南其他条款的一致性

- §14.1「横屏优先不等于只用宽度断点判断手机」：§1.1 用方向 + 短边 + 阶段三判据，不靠 `max-width:900px`。
- §9.3 动效原则：自转瞬时无过渡，提示淡出 ≤ 约 200 ms，减少动效保留静态高亮与文字。
- §13.1 设备与视口：A-4/A-5/A-6 沿用竖屏 375×667 / 390×844 与三档横屏 667×375 / 844×390 / 932×430；A-13 明确真机不可替代。
- §13.2「横竖屏切换不丢座位，不提交草稿，不无限弹提示」「帮助可点击，焦点可见；不靠 hover/颜色/声音传递唯一信息」「减少动态效果时仍能理解…」：分别由 A-7 / A-10 / §5 / A-11 覆盖。

### 8.3 文档处置

**不修改 4.2 原文**。本文是 4.2 在「通用横屏」目标下的细化规格；若用户希望把 4.2 的「手动旋转提示」措辞同步改写为「页面自转 + 转向提示」，需用户拍板后另立改动，本轮不擅自定稿（也不改任何其他 docs）。

3. 夸克（Android 12 / 华为 `ADY_AL00`）**实测拒绝**方向锁定（`docs/16` §1.3）。
4. 华为浏览器在系统强制旋转下把网页按竖屏宽度渲染成中间竖条、两侧黑边（`docs/16` §1.1）。
5. 现状竖屏为退化布局（`.rail{display:none}`）+「进入横屏」按钮 + 降级提示；用户明确不想要「弹个卡片让人自己转」。
6. 系统方向被锁死时，前端无可靠信号判断用户是否已物理转动手机（§2.3）——这是本方案用「一次提示 + 会话记忆」而非自动消失的根本原因。
