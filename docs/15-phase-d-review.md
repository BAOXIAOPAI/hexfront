## 4. D-01：棋盘手势吞掉内部按钮点击

涉及：`apps/web/src/camera.ts` 的构造函数、`handleDown()`、`handleUp()`、`handleClickCapture()`；`ui.ts` 中缩放和确认相关入口。

### 复现

1. 两个玩家进入独立房间并开始游戏。
2. 当前玩家选村庄及相邻道路，出现整组摆位确认。
3. 用鼠标点击“确认”：界面没有变化，摆位没有提交。
4. 对同一个按钮按 Enter：摆位成功，轮到下一位玩家。
5. 点击“放大棋盘”：SVG viewBox 没有变化。

### 原因

相机监听整个 `.board-stage`。该舞台同时包含棋盘、缩放工具、确认条、强盗和弃牌等控件。按钮上的 pointer 事件也进入棋盘手势流程，随后原生 click 被捕获监听阻止，无法到达按钮自己的处理函数。

浏览器已确认摆位确认和缩放受影响；其余舞台内按钮属于同一风险范围，应逐一复验，不能直接写成全部已实测失败。

### 修复建议

- 明确棋盘输入区域与界面控件边界：可绑定专用棋盘输入层，或在手势入口统一排除交互控件及标记的浮层区域。
- 同时检查 pointer capture、wheel、click 抑制；不能只在按钮 click 中 stopPropagation，因为捕获处理早于该监听执行。
- 保留真实拖动后的误点击抑制；按钮点击不能触发附近棋盘候选。

### 复验标准

- [ ] 鼠标与触屏均可确认/取消摆位和建造。
- [ ] 放大、缩小、回到全局均改变正确的相机状态。
- [ ] 弃牌加减/提交、强盗玩家选择均能点击。
- [ ] 点击任何浮层按钮不会顺带选择棋盘位置。
- [ ] 拖动超过阈值后抬手不建造，双指结束后不误选。

## 5. D-02：摆位提示框被拉伸

涉及：`apps/web/src/layout.css` 的 `.board-stage .setupbar, .board-stage .robberbar`，以及旧 `styles.css` 中对应定位规则。

844×390 横屏实际读取到：setupbar 的 top=8px、bottom=14px、height=324px、width=228px。画面中它成为覆盖棋盘中心的大块浅色面板。

新布局设置 top，却未清除旧 bottom，浏览器据此拉伸元素。旧媒体查询、动画 transform 也需要一起核对，不能只验证新文件里单独一条规则。

修复时应明确重置冲突的 inset、尺寸和定位属性，使提示按内容高度呈现；强盗条和弃牌面板也需逐状态检查。普通说明应尽量不拦截地图输入，含按钮区域则必须保持正常可操作。

复验：

- [ ] 667×375、844×390、932×430 横屏中提示为紧凑条，不形成纵向遮挡。
- [ ] 摆位、强盗、弃牌、建造确认同时按预期层级呈现，不遮住所需目标。
- [ ] 页面初次动画结束后与后续 STATE 更新后的布局一致。

## 6. D-03：骑士与筑路选择丢失

涉及：`apps/web/src/panels.ts` 中选点回调、`open()`、`renderKnight()` 和 `renderRoads()`。

骑士回调先赋值 `knightTile`，再执行 `open('knight')`；open 会调用 renderKnight，而 renderKnight 将 knightTile 设为 null。随后第二步渲染发现没有地块而退出。定向运行结果仍是“去棋盘选地块”的首步。

筑路有同样顺序：赋值 pickEdges 后 open('roads')，renderRoads 将数组清空，第二步显示“已选 0 条路”。确认无法完成所选操作。

修复应区分“开始一次新操作时初始化”与“展示/恢复当前步骤”。普通渲染不应无条件清空选点结果；不建议通过更多调用顺序补丁掩盖状态生命周期。

复验：

- [ ] 骑士选点后保留地块，进入合法抽牌对象选择，并能成功提交。
- [ ] 抽牌对象只包含所选地块相邻且有牌的玩家；无合法目标时正确处理。
- [ ] 筑路保留所选道路，第二条候选基于假设第一条的合法状态计算。
- [ ] 一条/两条提交、取消、广播更新、再次打开均有确定结果。
- [ ] 用真实 UI 完成至少一次骑士和一次筑路，不仅验证面板能打开。

相邻抽牌对象及筑路候选属于相关复验要求；本次没有证明它们已全部正确。

## 7. D-04：强盗待移动时无法切换为建造选点

涉及：`apps/web/src/ui.ts` 的 `boardOverlay()`、`applyHit()` 与建造模式切换。

已确认目标规则：有人未弃牌时暂停行动；全员弃完后恢复建造/交易/兑换；强盗完成前禁止发展卡和结束回合。

当前 boardOverlay 在检查 buildMode 前就返回强盗地块候选，applyHit 也优先处理强盗。结果是按钮虽允许进入建造，棋盘仍处于移动强盗模式。此项为源码确认，尚未在浏览器完整构造掷 7 后的场景复现。

建议将“强盗尚未完成”作为规则待办，将“当前正在执行建造还是移动强盗”作为本地交互模式，分别管理。模式切换不清除强盗待办，也不能绕过服务端结束限制。

复验：

- [ ] 弃牌完成后先建路/村/城可以正常选点并提交。
- [ ] 可暂时交易/兑换，再返回强盗任务。
- [ ] 强盗未处理不能结束回合或使用发展卡。
- [ ] 所有人尚未弃完时，以上资源变更仍由服务端拒绝。

## 8. D-05：报价冷却控件未更新

涉及：`apps/web/src/panels.ts` 的 tick、renderOffers，以及 drawer-body/drawer-foot。

tick 在 drawerBody 内查找 `#offer-send`，实际按钮在 drawerFoot，导致找不到按钮。设置本人 nextSendAt 为未来 3 秒、编辑一份非空报价后，运行结果仍为“发送报价”，disabled=false。

修复建议：直接持有或在正确容器定位按钮，统一计算发送条件：连接已同步、普通行动阶段、无弃牌锁、合法对象、内容非空、冷却结束。不要让定时更新仅检查冷却而意外解除其他禁用条件。服务端保持权威校验。

复验：

- [ ] 发送后显示冷却倒计时且不可重复发送。
- [ ] 冷却期间草稿可编辑；结束后仅合法非空报价可发送。
- [ ] 断线、弃牌锁、回合变化后按钮状态及时更新。
- [ ] 刷新/重连不能绕过服务端冷却。
- [ ] 到期、替换或清除报价后，不让另一条接受按钮顶到手指下造成误点。

最后一项是既定指南的回归要求，本次未完成其浏览器并发验证。

## 9. D-06：前台恢复缺少状态核对

涉及：`apps/web/src/main.ts` 的 onResume、`net.ts` 的 ping 与重连、`apps/server/src/server.ts` 的 PING 处理。

当前前台恢复分支在客户端认为连接为 open 时发送 PING，文案称正在等待服务端视图核对；服务端只回复 PONG。该链路没有请求完整视图/报价快照，没有等待探活回复的明确超时恢复路径。已经重连时 WELCOME 能恢复视图，与本问题不是同一条路径。

不能据此断言每次切后台都会失步；本次确认的是实现未提供所声明的主动核对保障，半开连接等场景仍需真机复验。

修复建议：设计明确的恢复请求与完整快照响应，或采用受控重连恢复；核对完成前有清晰状态。探活应有超时及连接重建策略，不能只依赖 socket.readyState。恢复不自动重放建造、接受报价等旧意图，过期报价不得续期。

复验：

- [ ] 切后台再回前台，取得当前权威视图和未过期报价。
- [ ] 网络切换或半开连接不永久停在“正在核对”。
- [ ] 提交后确认前断线，回来能核对结果，不重复执行。
- [ ] 后台超过 10 秒的报价正确过期。
- [ ] 真机后台电话/语音房、锁屏和标签回收后重开均有记录。

## 10. 布局收尾：应在 D 完成

本次横屏画面还观察到：顶部玩家卡片超出顶栏，倾斜资源卡占据右栏较多高度，底部按钮文字被挤为两行。它们影响可读性和操作空间，不能全部归为 E 的素材美化任务。

建议先限定顶部玩家条高度和内容层级，资源改为紧凑图标与数量，并保证固定行动按钮文字完整可读。使用长房间号、长昵称、四位玩家和大资源数量复验，避免只在双人短昵称下成立。

本次只测了一个明确横屏尺寸，不声明其余断点已通过。小横屏、竖屏、桌面及安全区仍按 `10` 的设备矩阵执行。
